# STS2 Guide 设计决策笔记

写给要讲清楚这个项目的人：每个关键决定当时有哪些选项、为什么这样选、遇到了什么问题、结果怎么量。
数字都来自仓库里的脚本和提交记录（2026-10-31），可以复现。

## 30 秒版本

《杀戮尖塔 2》的本地决策副驾驶：只读 Mod 把游戏状态导出成 JSON，本地 Python 服务在 300 ms 内算出选牌、路线、
篝火、商店、古神遗物的建议，再写回游戏里的面板显示。核心不是大模型，而是一个**确定性的评分引擎**：
机制事实从游戏程序集（IL）里读出来并经过独立复核，评分用“选择之后牌组能力 vs 接下来战斗的需求”来算，
所有参数都用真实对局记录做离线评估，并且坚持“不知道就说不知道”（公开缺口，不编造分数）。

## 1. 产品边界：只读、本地、不代打

- **问题**：辅助工具最容易出事的是改游戏、改存档、联网传数据、替玩家操作。
- **决定**：Mod 只用 Harmony Postfix 读状态，`affects_gameplay: false`；不点击、不改存档、不联网；建议只显示，玩家自己选。
- **代价**：所有信息只能从游戏对象读，读不到的就只能标“未知”；也不能在游戏里试错。
- **追问**：为什么不用内存读取／屏幕识别？——内存读取不稳定且像外挂；屏幕识别会出错。Postfix 读的是游戏自己的模型对象，
  类型和成员都先用程序集核实过（`tools/Sts2ApiProbe`）。

## 2. 架构：Mod → 文件交换 → Python 服务 → 游戏内面板

- **结构**：C# Mod 把完整状态写成 JSON（协议 v9，有 JSON Schema），Python 后台处理后写回建议文件，Mod 读回显示。
- **为什么用原子文件而不是本地 HTTP**：不开端口、两边崩溃互不影响、每个事件都能录下来回放测试。代价是要自己处理
  版本、顺序和过期（`run_id + event_id + 候选稳定 ID` 校验，旧建议不显示）。
- **版本一致性**：发行清单里有 Guide／游戏／Mod／协议／数据／策略各自的版本，再算出一个 `release_fingerprint`
  钉进 Mod 和协议示例；任何一项不匹配就清掉建议、停止推荐。能力开关（`capabilities`）在 Mod 构建时编译进去，
  没真机验收的能力不会显示。
- **踩过的坑**：Windows 的 `autocrlf` 改了数据文件换行，导致重新检出后哈希对不上清单 → 加 `.gitattributes` 固定这些文件为二进制。

## 3. 为什么评分用确定性引擎，不用大模型

- **约束**：实时决策 P95 ≤ 300 ms；同样的局面必须给同样的建议；要能解释每一分从哪来；不能编造卡牌效果。
- **决定**：评分全部是确定性计算（Python），大模型只允许做“玩家主动展开时的异步解释”，不进入实时主链（见 AGENTS.md）。
- **追问**：那大模型能做什么？——解释、问答、规划这类“读引擎结果”的工作；把引擎当工具调用，比让模型自己估分可靠。

## 4. 评分模型：从“加减分规则”到“牌组适合度”（ADR 0001）

- **问题**：v1 是“50 分 + 几十条独立加减规则”：量纲不统一、阈值断崖、同一事实重复计分，跳过另有公式。
- **决定**：每个选项（包括跳过）都评为“做了这个选择之后”的牌组适合度：
  - 牌组能力：六个维度（前期输出、群伤、防御、成长、循环、能量），每张牌按每回合被抽到的概率、能量够不够打来折算；
  - 局面需求：从真实遭遇池和 Boss 数据，按推荐路线上接下来的战斗算出；
  - 满足度曲线是凹的：低于需求时每单位值 1～2，高于需求时最多 0.25——缺口的惩罚比富余的奖励重。
- **不做战斗模拟**：用每回合期望的解析计算，快、可解释、可复现；代价是忽略出牌顺序等细节。
- **后来补的**：前瞻（第 7 条）、战斗长度随输出变化（输出越高战斗越短、受到的伤害越少）。

## 5. 事实只来自游戏程序集，并且两个人看

- **问题**：攻略站和描述文字会过时、会写错；早期用正则从描述里抽“协同”，错误很多。
- **决定**：写了一个只读的 IL 提取器（`tools/Sts2FactExtractor`），每张卡牌／遗物／怪物的机制事实都对照 IL 写成结构化数据
  （`data/assembly/facts.json`），并锁定该类的代码指纹——游戏更新时只让改动过的条目失效。
- **复核流程**：每条事实由起草者写，另一个独立的审核者对照 IL 逐条复核，分歧由开发者按 IL 裁决并写明。
  最近一批 102 个古神遗物：99 条同意，3 条按审核者的 IL 证据改正（例如“附魔只在能附到新牌时保留”）。
- **追问**：攻略站完全不用吗？——只用来交叉核对，冲突时以 IL 为准并记录。

## 6. 不知道就说不知道（公开缺口）

- **规则**：缺数据不给分、不用默认值；能算一部分时，分数是“已计入部分”的下限，并写明哪部分没算。
- **信心值的重新定义**：一开始“有任何缺口就低信心”，结果 79 个标准局面全是低信心，信息量为零。
  改成“只有可能改变这次选择的缺口才降低信心”：领先不足半分算接近平手；排在前面、只部分计分的对手在 1 分以内也算低信心。
  改后标准答案集 86% 为中等信心。
- **踩过的坑**：古神遗物估值一开始把“加入一张部分计分的牌”的缺口丢了（例如故事书给的牌每打一次失去 2 最大生命，
  这部分引擎不会算），选项看起来是完整计分 → 改成把加入牌的缺口带到选项上。

## 7. 前瞻：用固定种子抽样，结果可复现

- **问题**：只看“现在的牌组”会低估构筑型的牌——它们的价值在后面的选择里。
- **决定**：按本幕剩余战斗，抽样之后的卡牌奖励（按程序集的稀有度机率），用同样的适合度贪心选；所有候选共用同一组抽样，
  种子来自决策 ID，所以同一局面永远同一结果。
- **预算**：抽样情境数是参数；为满足延迟，从 6 降到 4，在 562 个情境上检验命中数没有下降。

## 8. 评估：先有评估框架，再改模型

- **数据**：
  - 标准答案集：79 个真机选牌局面，人工确认过答案；
  - 对局历史：游戏自己的 `.run` 记录，导入成 483 次选牌、260 次篝火、86 次商店删牌、97 次古神选择、111 次商店。
- **原则**：参数人工设定，不按个别局面拟合；要检验时用没参与设定的那一半数据（例如篝火“60% 生命以下休息”的门槛，
  从一半对局读出，在另一半上与玩家一致 80.6%～87.3%）。
- **指标**：首选与玩家／标准答案一致的比例、明显错误排第一的次数、“买或离开”一致率等；同时报告覆盖率（多少能评分）。
- **诚实的数字**：选牌标准答案集 34/79（43%）；古神遗物首选与玩家一致 38%；商店“买或离开”一致 78%。
  玩家的选择不是标准答案，这些数字用来发现系统性偏差，而不是拿来硬凑。

## 9. 取消社群评分

- 曾经用社群 tier 和统计分数当先验。决定取消：它把“相关性”（大家常拿）混进“因果”评分（这副牌需要什么），
  而且无法用局面解释。试过混合排序在历史上 +11 次命中，仍然拿掉——可解释性和独立性优先。

## 10. 性能：先测量再优化

- **问题**：发行审查测得选牌 P95 约 450 ms，超过 300 ms。
- **做法**：cProfile 显示前瞻占 2/3 时间（每次推荐约 180 次引擎计算）。依序：
  1. 同一决策内按“牌组组成”缓存引擎结果；
  2. 同一张牌的多张副本只解析一次效果（引擎对副本是线性的）；
  3. 卡牌名称和目录查询按策略生命周期缓存；
  4. 抽样情境 6 → 4（已验证不降命中）。
- **怎么证明没改坏**：缓存和“副本只算一次”之后，562 个情境的输出逐字节相同；之后把其余求和也按副本合并，
  有 2 个情境的前瞻差值因为浮点求和顺序差了 0.02，推荐没有变。
- **怎么量**：这台机器速度随负载差一倍，所以改用 CPU 时间、并且新旧版本交替测量；同负载下 P95 469 → 250 ms。
  脚本：`scripts/benchmark_card_reward_latency.py`。

## 11. 金币和生命怎么换成“分”

- **问题**：商店、事件、古神遗物要比较“牌组变强”和“金币／生命”，必须有同一个尺度。
- **决定**：锚点用引擎在历史数据上量出来，不按玩家的选择拟合：
  - 金币：值“之后的商店能买到的东西”，先买最划算的。每间商店每 50 金币一段的边际价值取中位数（越往后越低），
    再按之后预计的商店数（每幕约 1.2～1.3 间，按走到下一幕的比例加权）合并 → 金币越多每枚越不值钱；
  - 生命：篝火规则说 60% 生命时休息（回 30% 最大生命）和锻造打平，所以 30% 最大生命 ≈ 最佳升级的价值；
  - 最大生命：游戏代码里加最大生命会同时回同样多的血，每次休息回 30% 最大生命，所以还要加上之后每次休息多回的部分。
- **效果**：最早用固定的“每 100 金币几分”，商店里引擎有 800 金币还建议离开（离开 37 次 vs 玩家 18 次）；
  改成递减边际价值后“买或离开”一致率 65% → 80%，离开次数 17 vs 18。

## 12. 选遗物：期望值、共同随机数、时间加权

- **问题**：古神遗物的价值很多在“拾起那一刻”（删牌、变牌、加金币）或“之后的战斗外”（每三场战斗后随机升级等）。
- **决定**：
  - 把拾起和战斗外效果也写成经复核的事实；随机结果（变出什么牌、拿到什么遗物）用抽样取期望；
  - 之后才发生的效果按“它之后剩下的局程 ÷ 现在起的局程”加权（后面的幕按走到的比例），不在本幕结束时硬切。
- **踩过的坑**：每个选项各抽 6 个样本时，“变化一张牌”的平均值会因为运气摆动约 2 分，足以翻转推荐。
  改成同一决策内所有选项对同一卡池用同一组样本（共同随机数），样本加到 16，多步随机的样本总数不相乘
  （同时一次古神选择最慢从 3.5 秒降到约 0.85 秒，单个遗物最多约 0.2 秒）。

## 13. 用多个 Agent 起草和复核事实

- 102 个遗物分三批并行起草，再由另外三个独立 Agent 对照 IL 复核，开发者裁决分歧。
- **流程上的教训**：Agent 会因为额度中断；一开始它们先读完所有代码才写入，中断后什么都没留下 →
  改成“每完成一条就存档并校验”。共享暂存目录会被别的 Agent 覆盖 → 各自用独立目录。

## 14. 数据收集与隐私

- 托盘菜单“导出对局记录”把游戏自己的 `.run` 打包成 zip 给作者；压缩包里的路径从 Steam ID 目录之下开始，不含账号信息；
  每台电脑一个随机收集者编号区分玩家；导入时同一局（种子＋开始时间）只算一次，并只接受带清单的压缩包、
  只解出 `runs/**.run`，防止恶意路径写到外面。

## 15. 删牌校准（暂停前最后一项）

- **问题**：历史 71 次商店删牌，引擎的选择与玩家一致只有 15%；其中 24 次引擎选的是“部分效果没算进去”的牌。
- **原因**：这种牌被低估，所以“删掉它”的收益被高估。
- **决定**：自选删除／变化时优先只在完整计分的牌里选 → 一致率 25%（计入前瞻 30%）。
- **剩下的问题**：玩家删打击时，引擎常想删防御（防御不足的权重偏重）；试过调整会伤到选牌，暂不处理。

## 已知局限（面试时主动说比被问出来好）

- 引擎是每回合期望，不模拟出牌顺序；能量不够时按比例分配，而不是像人一样先打最好的牌。
- 药水、事件选项还没有事实；有些附魔、卡牌奖励修正、地图改动只公开为缺口。
- 与玩家的一致率只有 30%～45% 左右；玩家不是标准答案，但这说明引擎在一些地方系统性地跟人不一样（例如删牌）。

## 如果重来一次

- 评估框架和延迟基准从第一天就进 CI，而不是发行审查时才发现超时。
- 早点把“随机结果的抽样噪声”当成需要测量的东西（共同随机数应该一开始就用）。
- 参数表会更少：很多参数后来证明可以从更少的锚点推出来（例如金币曲线）。
