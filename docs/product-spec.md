## 2. 产品定义

STS2 Guide 是一个面向《Slay the Spire 2》的本地、只读、状态驱动决策 Agent。

用户正常启动游戏，再单独启动 `STS2 Guide.exe`。程序在后台运行，通过只读 Mod
获取当前局面，在选牌界面左侧抽屉显示本地计算的推荐分。用户仍然在游戏中自行操作，
系统不点击、不代打、不修改存档和游戏状态。

P0 的核心不是攻略问答，也不是大模型对话，而是完成一个稳定、低延迟、可解释的
选牌推荐闭环：

```text
游戏状态
  → 只读 Mod 感知
  → 本地 Agent 维护当前局状态
  → 本地规则与数据源计算候选分
  → 游戏内面板显示候选牌和“跳过”的推荐分
```

它仍然属于 Agent 项目，因为系统具备：

1. 感知：监听游戏状态和决策场景；
2. 状态：维护可恢复的当前局检查点；
3. 策略：根据牌组、遗物、路线需求等信号调用本地推荐工具；
4. 行动：主动向用户展示建议；
5. 生命周期：随一局游戏创建、恢复和结束；
6. 扩展工具：以后可按需调用 RAG/LLM 解释“为什么”。

实时 Agent 不以 LLM 为成立条件。P0 不允许网络和大模型成为实时推荐链路的依赖。

首个公开版本不是“当前开发电脑能运行”的同义词，而是 Windows Public Beta。它的明确
支持范围为：

- Windows、STS2 单人模式和安装包兼容清单中列出的精确游戏版本；
- 原版五个角色全部可用，不以只完成铁甲战士作为公开发布门槛；
- 用户能力冻结为选牌建议与路线建议，Neow、商店、篝火和其他决策后续迭代；
- 原版内容加 STS2 Guide 自己的只读 Mod；其他玩法型、内容型 Mod 不属于首版兼容承诺；
- 实时推荐完全本地运行，默认不上传遥测、牌组、存档或局内事件。

“当前版本”必须由发行兼容清单精确表达，不能写成永久范围。本机游戏已于
2026-07-30 更新为 `0.109.1`；该版本只有重新完成程序集/API、协议、自动测试和真机门禁
后才能进入支持清单。在此之前必须失败关闭，不能沿用 `0.108.0` 的真机证据继续推荐。

## 3. 用户体验

### 3.1 启动

P0 内部验收阶段仍允许用户分别启动游戏和无主窗口的 `STS2 Guide.exe`。首个公开
Beta 的目标体验升级为：

1. 安装程序自动定位或让用户选择 STS2 目录，并安装可核验的 Mod 与 Guide；
2. 用户可以先启动 STS2，也可以先启动 `STS2 Guide.exe`；
3. Guide 以单实例托盘程序驻留；检测到游戏后启动实时 Worker，游戏关闭后停止 Worker，
   但托盘继续低占用待机；
4. 再次运行 EXE 只唤起已有实例，不生成第二个 Host；
5. 只有用户从托盘选择“完全退出”时，控制器和全部 Worker 才一起结束；
6. 托盘提供连接、游戏版本、Mod/协议/数据版本、更新和脱敏诊断状态，但不替代局内建议。

最终用户不应手动启动 Python、FastAPI、Vite 或终端脚本。Vue 前端不属于 P0
运行依赖。

### 3.2 选牌界面

- 推荐面板由 Mod 创建为 Godot `Control`，锚定游戏原生选牌界面；
- 面板采用贴住视口左边缘的半透明抽屉，宽度根据内容与视口自适应，并设置合理的最小值、最大值和视口占比；
- 抽屉默认展开，点击右缘箭头后向左滑出并仅保留贴边按钮，再次点击滑入；
- 按游戏原始顺序显示实际数量的候选牌名称和“跳过”；
- 每项只显示 `0–100` 的“推荐分”，不显示长解释、置信度或社区分拆；
- 四个分数互相独立，不要求总和为 100，也不表示胜率；
- 分数只保证同一次真实决策内的候选可比较，不承诺跨局、跨角色或跨版本的相同数值
  具有相同含义；
- 最高分项突出显示；
- 数据不足时显示 `--`，不得伪造精确值；
- P0 标准场景是普通战斗/奖励后的三张牌加跳过；Neow 祝福等开局特殊决策不属于
  P0 推荐范围，若出现同类选牌 UI，必须安全隐藏或显示 `--`，不得显示上一屏或错误候选；
- 选择完成或界面关闭后自动隐藏；
- 除抽屉开关外，面板只显示信息，不覆盖原按钮，不接受替用户做选择的交互。

P0 先以真机效果为准确定间距、字号、颜色和高亮方式，视觉参数不写死为产品约束。
在面板不遮挡原生操作区域的前提下，字号应优先保证窗口模式下的可读性。

### 3.3 长期产品方向：实时策略副驾驶

P0 的选牌闭环是第一个可交付纵向切片，不是产品的最终边界。STS2 Guide 的长期形态是
一个本地、只读、主动感知关键决策的实时策略副驾驶，而不是攻略问答机器人、自动代打
工具或若干互不相干的评分面板。

产品围绕一局游戏形成连续闭环：

```text
感知真实游戏状态
  → 维护当前局世界状态
  → 识别当前决策场景
  → 调用对应的本地策略工具
  → 比较实际可选候选
  → 在统一游戏内抽屉主动展示建议
  → 观察决策关闭并继续维护状态
```

P1 及以后覆盖路线、Neow、商店、篝火、Boss 遗物和事件，但仍由用户自己操作。
默认界面保持安静，只显示即时排序和推荐度；解释属于按需展开的第二层，不得阻塞实时
建议。RAG/LLM 只可为解释提供攻略证据，不能成为决策 Agent 成立的前提。

### 3.4 统一决策体验

当前左侧选牌抽屉长期升级为统一的 `Context Drawer`：

- 没有受支持决策时隐藏或保持最小化；
- 只显示当前真实场景的候选，不跨场景复用上一条建议；
- 根据选牌、地图、商店、篝火等场景切换内容，而不是新增多个浮窗；
- 用户界面名称使用“策略侧栏”；`Context Drawer` 只作为内部工程名称；
- 默认展示排序、推荐度、必要风险提示和最关键的 2–3 条加减分原因；
- 用户主动展开后才显示关键因子、替代方案和可选攻略解释；
- 状态、候选或身份校验不足时显示 `--` 或隐藏，绝不猜测。

路线模式在策略侧栏内切换，首版使用三个目标型软偏好：

- 智能均衡：按当前局面自动平衡生存和成长；
- 稳健生存：降低路线风险，倾向休整并减少高风险节点；
- 激进成长：在安全底线内提高精英和高收益节点权重。

模式不是硬命令，不能在明显无法承受时强迫推荐危险路线。同一局保存继续后保留当前
模式，胜利、失败、放弃或新开一局后恢复“智能均衡”。玩家没有按建议选择时，Guide
必须把实际进入节点作为新事实，废弃旧路线并保留当前模式重新规划。

地图只绘制一条从当前真实节点通往本幕 Boss 的“当前规划”，突出下一节点；不同时绘制
备选完整路线。路线在节点、牌库、HP、遗物、药水或其他重要状态变化后重新计算。覆盖层
优先使用独立只读 Godot 绘制层；只有经程序集和真机验证后才可复用游戏坐标/渲染 API，
不得模拟原生绘制按钮、修改用户涂画或拦截地图点击。

## 4. P0 系统架构

```text
┌──────────────────────── STS2 进程 ────────────────────────┐
│                                                           │
│  游戏状态 ──> 只读 C# Mod ──> 临时事件文件                │
│      │                                │                   │
│      └── 原生选牌界面 <── Godot 推荐面板 <── 建议文件      │
│                                                           │
└───────────────────────────────────────────────────────────┘
                                   ▲
                                   │ 本地文件协议
                                   ▼
┌──────────────────── STS2 Guide 后台 EXE ──────────────────┐
│ 协议校验 → 当前局检查点 → 本地推荐器 → 原子写回建议       │
│                    │                                      │
│                    ├── 本地社区先验                        │
│                    ├── 结构化卡牌/遗物数据                 │
│                    └── 当前局状态规则                      │
└───────────────────────────────────────────────────────────┘
                     │
                     ├── 当前局：单一可替换检查点
                     └── 结束后：仅 SQLite 最终结果摘要
```

### 4.1 只读 Mod

负责：

- 读取角色、难度、楼层、生命、金币、能量；
- 读取完整牌组、升级、附魔和负面状态；
- 读取遗物及其动态状态、药水、Run Modifiers；
- 读取选牌候选、候选顺序、是否允许跳过、奖励来源；
- 监听选择、跳过、界面关闭和一局结束；
- 捕获当前节点、地图节点、真实边、可选下一节点和 Boss；
- 将事件原子写入本地目录；
- 读取建议并绘制游戏内面板。

不负责：

- 计算分数；
- 调用网络、LLM 或数据库；
- 修改游戏状态、选项、存档或用户输入；
- 自动点击或代替用户操作。

### 4.2 后台 EXE

负责：

- 启动并托管文件桥接、协议校验、检查点和推荐器；
- 对事件做顺序、重复和过期检查；
- 从本地数据源加载结构化先验；
- 在本机完成评分并原子写回建议；
- 游戏中断后恢复同一局；
- 在胜利、失败或放弃时清理中间状态并保存最终摘要；
- 统一记录本地日志和可诊断错误。

P0 可以由 Python 打包为单一后台 EXE，不要求为了“桌面原生”重写全部推荐逻辑。

公开 Beta 的托盘控制器和实时 Worker 可以位于同一个 EXE/进程，也可以是受控子组件；
无论实现形式如何，都必须由用户级单实例机制统一拥有生命周期。游戏关闭时 Worker
停止，托盘继续待机；完全退出必须等待并回收所有后台任务，不允许留下旧 Host。

### 4.4 版本、更新与兼容性

发行包必须携带唯一兼容清单，至少记录：

- Guide 版本；
- 支持的精确游戏版本和当前程序集哈希；
- Mod 版本；
- Mod/Host 协议版本；
- SQLite 静态数据快照版本；
- 推荐策略版本。

Mod、Host、数据库或协议任一项不匹配时必须清除旧 advice、停止推荐并指出具体不兼容项。
未知游戏版本不得“尽力继续”。托盘可以提供可关闭的更新检查，但更新模块只读取版本
清单，不上传任何局内数据；实时 Mod 和推荐 Worker 始终不依赖网络。

首版正式支持原版内容。检测到第三方玩法或内容 Mod 时标记为未验证环境；未知实体显示
`--`，不得按名称猜测。无法可靠确认环境时失败关闭。

### 4.3 Vue、FastAPI、RAG 和 LLM

- Vue 保留为以后攻略问答或历史查看的候选界面，不进入 P0 实时链路；
- FastAPI 可作为开发调试接口保留，但最终 P0 启动不依赖独立 API 进程；
- RAG 只处理攻略语义检索和可选解释，不决定实时分数；
- LLM 以后只能用于用户主动展开的解释，不得阻塞或改变实时基础推荐。

## 5. 数据边界

不同数据按用途存放，不能因为“都能存”就统一塞进向量库或关系库。

| 数据 | 存储 | 生命周期 | 原因 |
|---|---|---|---|
| 卡牌、遗物、药水、角色、敌人、遭遇、事件、章节、机制和来源元数据 | SQLite | 长期 | 稳定 ID、过滤、关联、规则计算和版本查询 |
| 社区结构化统计 | SQLite（源快照可为 JSON） | 长期 | 数值查询，不需要语义检索 |
| 本地人工整理的 tier 数据 | Git 忽略的 JSON | 用户本机 | 可选私有输入，不随项目分发 |
| 攻略正文和语义切片 | 原文快照 + 向量索引 | 长期、可重建 | 用于 RAG 语义检索 |
| 当前局完整状态 | 单一原子 JSON 检查点 | 当前局 | 需要恢复，不需要历史查询 |
| 待处理事件 | 临时事件队列 | 处理后删除 | 避免快速事件覆盖，不作为历史 |
| 每次选牌分数和选择过程 | 默认不持久化 | 当前决策 | P0 不收集训练样本 |
| 最终对局摘要 | SQLite | 长期 | 战绩查询和以后统计 |

### 5.1 当前局检查点

每一局只维护一个可替换检查点，而不是不断向 SQLite 追加状态历史。

协议必须明确区分“权威完整快照”和“事件通知”：

- 完整快照是当前局事实，事件只负责通知状态或决策发生变化；
- 开局、继续游戏、中途接入和关键决策出现时，必须能取得同一 revision 的完整关键状态；
- 每个决策绑定 `run_id + state_revision + decision_id + 候选稳定 ID`；
- 不得把新牌库与旧地图静默拼成一个看似完整的 `WorldState`；
- 关键数据（角色、牌库、候选、Run/决策身份）缺失时停止推荐并显示“正在同步”；
- 非关键上下文缺失时可以降级，但必须列出 data gap，并让对应因素不参与加减分；
- Host 可在游戏前、游戏后或一局中途启动；没有足够快照时等待同步，不复用上一局建议。

检查点至少包含：

- 可跨游戏重启识别的稳定游戏 Run ID；
- 最近处理的事件序号；
- 当前角色、难度、章节、楼层、生命、金币和能量；
- 当前牌组、遗物、药水、Modifiers；
- 当前节点和已读取的地图快照；
- 当前未关闭决策及其候选；
- 游戏版本，仅用于兼容性诊断。

写入必须使用“临时文件 + 原子替换”。游戏或后台程序异常退出后，只要该局仍可继续，
下次启动就恢复检查点；不能继续或已结束时清理检查点。

当前 Mod 每次启动随机生成的 ID 不能满足恢复要求。P0 必须从游戏可稳定读取的数据
构造或取得 Run ID，并验证不会把两局游戏合并。

### 5.2 最终结果

胜利、失败或放弃后：

1. 写入一条最终结果摘要；
2. 确认写入成功；
3. 删除检查点、临时事件和未完成建议；
4. 不保留逐楼层状态、逐次选牌历史或完整事件流。

最终摘要字段：

- 结果：`win` / `loss` / `abandon`；
- 角色；
- Ascension；
- 最终楼层；
- 最终分数；
- 开始和结束时间；
- 最终牌组；
- 最终遗物；
- 最终药水；
- 游戏版本（内部保留，默认不展示）。

P0 不进行个人习惯学习，也不积累 `decision_outcomes` 训练样本。以后若加入个性化，
优先保存风险偏好、精英路线偏好、牌组精简程度等聚合特征，而不是完整原始对局。

## 6. 本地数据源策略

### 6.1 可随项目使用的数据

- Spire Codex 的结构化实体和社区统计作为默认可重建来源；
- 本项目自己的透明规则、卡牌标签和协同表；
- 经允许发布或项目自行创作的攻略文本。

Spire Codex 只作为开发期/构建期数据源，最终实时后台不得依赖联网查询。导入流程应：

- 优先使用按语言提供的批量 JSON 导出，并记录来源 URL、抓取时间、内容哈希和数据版本；
- 把卡牌、遗物、药水、角色、敌人行动、遭遇池、事件选项树、章节和机制常量作为
  结构化事实导入 SQLite；
- 保留原始 JSON 为可重建快照，但不把第三方图片资源或完整游戏资源打入产品；
- 对 API 缺失、字段变化和不完整记录安全降级，不能在运行时临时请求网络补数据；
- 遵守 Spire Codex API 条款和 Mega Crit 游戏数据权属说明，并在发布物中保留数据来源说明。

每个发行版携带与兼容清单绑定的 SQLite 快照。玩家运行时只从该本地数据库查询；游戏
版本变化后的结构化实体、效果标签和风险常量只能通过新版 Guide 更新，不能在玩家电脑上
临时抓取。社区数据始终是可移除的弱先验，缺失时推荐链路必须正常工作。

Spire Codex 的社区攻略与游戏实体数据不能混为同一种授权来源。攻略正文只有在逐篇确认
作者、来源和可再分发边界后，才进入原文快照和向量索引；事件剧情文本的权威副本仍随
事件结构保存在 SQLite/源快照中，不因为文本较长就自动进入向量库。

### 6.2 本机 Mobalytics tier 文件

P0 允许像参考项目一样读取本地 tier 文件，但采用以下边界：

- 数据由开发者在本机人工整理，不编写自动爬虫；
- 建议路径：`data/local/mobalytics_card_tiers.json`；
- 路径加入 `.gitignore`，文件不提交、不打包、不随公开版本分发；
- 只保存推荐所需的卡牌稳定 ID、角色、tier、记录时间和来源地址，不复制网页正文；
- 文件缺失、过期或格式错误时，推荐器必须自动退化到 Spire Codex + 自有规则；
- 使用稳定卡牌 ID 关联，不以中文名、英文名模糊匹配；
- tier 只转为有限权重的基础先验，不能直接决定最终选择；
- 具体 tier 到分数的映射由本项目自行定义和测试，不复制 BoberInSpire 的常量。

建议的最小文件结构：

```json
{
  "schema_version": 1,
  "source": "mobalytics-manual-local",
  "source_url": "https://mobalytics.gg/slay-the-spire-2/tier-lists/cards",
  "captured_at": "2026-07-03T00:00:00+08:00",
  "entries": [
    {
      "card_id": "stable-card-id",
      "character_id": "stable-character-id",
      "tier": "A"
    }
  ]
}
```

这是一项“当前开发电脑优先”的 P0 取舍，不等于将第三方内容纳入项目许可证。
公开发布时默认不依赖该文件。

### 6.3 参考 BoberInSpire 的边界

[BoberInSpire](https://github.com/S0ul3r/BoberInSpire)只用于验证产品链路和理解
“Mod 导出状态 → Python 本地计算 → 覆盖层展示”的可行性。

可以借鉴：

- 本地状态导出和消费的产品思路；
- tier 只作为基础值，再结合当前牌组调整；
- 实时推荐不依赖 LLM。
- 公开源码中暴露出的“可能存在的游戏类型、事件和字段名称”只能作为 API 调研线索。

不得复制：

- 对方代码；
- 对方生成或硬编码的流派表；
- 对方具体权重、tier 分数锚点和数据文件；
- 对方 UI 资源或品牌表达。
- 对方通过名称搜索、动态反射或兜底猜测得到的字段，不能直接作为本项目的生产 API。

本项目的差异化是：游戏内 Godot 面板、稳定 ID、多流派信号并存、正式的跳过候选、
当前局检查点和结束后仅保留摘要。

## 7. 选牌推荐策略

### 7.1 输出定义

每次选牌输出四个同尺度候选：

1. 左侧卡牌；
2. 中间卡牌；
3. 右侧卡牌；
4. 跳过。

推荐分表示“这个选项对当前局面的适合程度”，不是胜率，也不是社区排名。

### 7.2 透明评分原则

P0 使用可追踪的有界加法模型，不把尚未校准的规则包装成概率：

```text
卡牌适配分
  = 50
  + 卡牌基础效果
  + 当前牌组功能缺口
  + 卡牌与牌组协同
  + 当前角色与遗物协同
  + HP、章节和近期路线压力
  + 有界社区先验
```

社区先验只负责在局面信号接近时提供弱排序，不使用固定百分比伪装精度，也不能单独
触发跳过。所有因子必须返回代码、增减值和解释，调权必须通过固定场景集和真机样例
验证，不能因少量个人对局自动学习。

内部必须保存每个候选的完整分数贡献和原因代码；策略侧栏只展示最终推荐分和最重要的
2–3 条原因。推荐分是当前局面下的相对辅助刻度，不是胜率。

当前局适配至少考虑：

- 卡牌的输出、格挡、抽牌、能量、成长、范围、费用变化和资源代价；
- 当前攻防缺口；
- 能量曲线与出牌负担；
- 抽牌、能量和资源循环；
- 候选与已有卡牌、遗物的协同；
- 章节、Boss 和已知路线对短期能力的需求；
- 升级、附魔和负面状态；
- 重复牌收益或冗余；
- 牌组膨胀代价。

社区高 tier 不能单独强制抓取，社区低 tier 也不能在强协同时被硬性禁止。

卡牌和遗物的效果标签属于结构化事实，写入 SQLite 并由稳定 ID 查询。标签优先从
结构化字段生成，描述规则只作为可版本化、可测试的补充；RAG 和 LLM 不参与实时
标签生成或评分。

路线压力必须按当前可选路径分别统计，再聚合为可达比例和平均风险；不能把互斥分支
上的精英、Boss 和小怪全部视为必经节点。同一威胁对同一候选只能产生一组路线因子，
不得同时叠加“通用危险”和“精英/Boss 危险”。

战前敌人信息必须区分“已知事实”和“遭遇估计”。当前 Act 的 Boss 可以按游戏提供的
稳定身份参与威胁建模；普通怪物和精英在进入战斗前不能被当成已知具体敌人。它们只能
依据当前 Act 的真实遭遇池、已确认的游戏规则和本局已击败精英集合计算候选威胁：
未耗尽的精英池应排除本局已击败精英，池耗尽后才允许出现重复可能。此模型必须输出
候选集合或聚合威胁，不能伪造下一战的确定敌人。

P0/P1 的敌人机制只用于改善选牌和路线的战前风险判断，不提供战斗内逐回合出牌建议。
静态敌人行为与机制可以进入 SQLite；P0 不保存敌人逐回合行动历史。

P0 读取并保留药水状态，但药水是一次性资源，其“提供某种效果”不等于“支持继续
抓取同类卡牌”。在建立经过场景验证的资源替代模型前，药水不参与选牌评分。

自身耗竭、虚无和“与虚无牌交互”必须是不同标签。只有明确区分效果提供者与收益方
后才允许计算协同；无法由当前局状态验证的条件标签只保存事实，不进入实时加分。

### 7.3 多流派并存

P0 不把牌组过早分类为唯一流派。推荐器同时维护多个协同信号：

- 每个信号由已有牌、遗物和资源状态提供证据；
- 证据越强，该信号对候选的影响越大；
- 多个信号可以同时生效；
- 没有足够证据时回到通用攻防、曲线和资源规则。

五个角色共享同一个评分内核，不复制五套规则。每个角色允许注册一个薄机制适配层，
只负责把充能球、星数、厄运及其他角色专属资源转换为通用、可解释的能力和协同信号。
公开声明“全角色支持”前，每个角色都必须通过：

1. 牌库、遗物、药水、HP、地图和跳过的参数化通用规则测试；
2. 角色核心资源与主要机制的专项固定场景；
3. 至少一次完整第一幕的真机状态、选牌和路线烟测。

### 7.4 跳过

跳过是正式第四候选，分数不得固定。它与卡牌使用同一 `0–100` 适配尺度，至少考虑：

- 保持牌组精简的收益；
- 当前牌组大小和重复度；
- 三张候选对牌组造成的冗余或负面影响；
- 当前牌组是否急需补强；
- 当前章节和即将面对的威胁；
- 候选中是否存在明确协同或关键功能牌。

社区先验不能单独把卡牌压到跳过之下。面板高亮必须服从推荐器给出的最终候选，
不得仅对包括不可用“跳过”在内的显示分数取最大值。

## 8. 协议与实时性

当前目标生产协议是 JSON Schema v9。v4 在既有状态、决策和地图结构上增加
`boss_encounter_ids`，用于表达游戏已知的当前 Act Boss 遭遇；v5 进一步分离不可变
`event_id`、稳定 `decision_id` 和候选实例 `candidate_id`。这些字段不能用于把普通怪物或
精英伪装成确定遭遇。v6 增加 `route_choice` 与真实 `origin_node_id`；v7 增加权威快照、
 成功提交 revision、生产者/游戏程序集身份和跨组件 release fingerprint；v8 增加显式
`guide_preferences.route_mode`，把用户选择的路线软偏好纳入同局权威状态；v9 将所有实时
决策迁移到严格通用候选 envelope，并增加类型化成本、效果与父子决策身份。Python 对
v1-v8 的兼容只用于离线录制回放；生产 Host 只接受兼容清单指定的精确 v9。

### 8.1 事件

P0 实际处理：

- `card_reward`；
- `decision_closed`；
- `run_ended`。

P0 同时正确捕获 `map_snapshot` 所需数据，但不输出路线推荐。商店、篝火、Boss 遗物
等决策事件进入 P1 后再成为推荐工具，不能仅因协议中预留名称就宣称已经支持。

临时事件队列用于避免快速事件互相覆盖。后台确认处理后应删除事件；队列不是审计库。

### 8.2 建议响应

建议协议至少包含：

- 协议版本；
- 对应 Run ID；
- 对应事件 ID；
- 候选稳定 ID 和原始顺序；
- 候选牌与跳过的推荐分；
- 最高分候选；
- 生成时间；
- 推荐器版本；
- 数据不足或降级标记。

Mod 必须拒绝显示属于旧事件、旧 Run 或候选不匹配的建议，避免“上一组牌的分数”
显示在下一组选项旁。

实时生产 schema v9 在 v7 完整状态基础上必须显式携带：

- `snapshot_kind = "complete"`，表示该事件中的状态是同一观察时刻的权威快照，不是增量；
- 单调递增的 `state_revision`，当前实现可以等于成功提交的 event sequence，但不能使用
  写盘失败的尝试次数；
- `producer_id`、`producer_version` 和游戏程序集 SHA-256；
- 规范化 `release_fingerprint`，覆盖 Guide、Game、Mod、protocol、SQLite 快照和 policy；
- Host 根据唯一发行兼容清单计算的兼容结果；Mod 只报告身份事实，不能自行宣称兼容。
- `guide_preferences.route_mode`，只允许 `balanced`、`survival`、`growth`；同局保存继续
  恢复，胜利、失败、放弃或新 Run 重置为 `balanced`。
- 通用 `candidates` envelope、类型化 `cost` / `effects` 和可选 `decision_parent`；生产
  处理链不得继续依赖 Card Reward 专用顶层 `options`。

Schema 与运行时模型必须使用相同严格类型。Schema 拒绝的字符串数字、`0/1` 布尔、
NaN/Infinity 或缺失关键快照字段，Pydantic/消费者也必须拒绝。v1-v8 只用于离线录制回放；
实时 Host 只接受兼容清单指定的精确生产版本。事件、当前局 checkpoint、advice 和 Mod
显示端必须核对同一个 release fingerprint；升级后不得把旧策略结果重新标记为当前兼容。

### 8.3 性能目标

- 实时推荐不访问网络；
- 本地事件被发现到建议文件写回的 P95 不超过 300 ms；
- 单次纯评分应明显低于总预算，并通过基准测试记录；
- 数据源加载在后台启动时完成，不能每次选牌重新解析全部文件；
- 推荐器异常时游戏继续正常运行，面板显示 `--` 或隐藏。

## 9. 路线能力边界

P0 只做正确采集，不做路线推荐。

必须采集：

- 当前节点；
- 完整节点列表；
- 节点类型和坐标；
- 游戏提供的真实连边；
- 当前可到达的下一节点；
- 当前 Act 的 Boss。

进入具体战斗前，地图节点只能说明普通战、精英或 Boss 类型。除已知 Boss 外，不得把
普通怪物或精英预测成某个确定敌人；后续威胁模型只能基于遭遇池和已击败精英排除规则
计算期望风险。

禁止：

- 读取失败时伪造“下一行全部相连”；
- 用猜测边运行推荐器；
- 在前端展示看似可用的三种路线策略；
- 将地图界面打开等同于地图数据已正确读取。

路线推荐在 P1 使用经过回放和真机验证的图数据实现，并与生命、牌组、遗物和章节需求联动。
建议结果只把当前最高推荐的完整路线叠加在真实地图节点和连边上，并随地图布局和视口变化
重新定位；其他候选只保留为内部排序事实，不绘制第二条路线。该叠加层属于 STS2 Guide 的
只读 Godot Overlay，不写入游戏原生“绘制/擦除/清除”数据，不覆盖玩家涂画，也不修改
存档；显示和隐藏由统一 `Context Drawer` 控制。

## 11. P1 计划

P1 在 P0 稳定后扩展“决策类型”，不先扩展模型复杂度。默认交付仍采用一个决策类型一个
完整纵向闭环。2026-07-31 用户明确决定在下一轮集中真机前批量完成后续自动层，因此允许
路线、Neow、商店、篝火与事件在同一个扩展任务中连续实现，但必须共用一次协议迁移、
一个生命周期、一个策略注册表和一个 Context Drawer；不得铺开多套半成品管线或复制
`card_reward` 处理分支。

批量实现只改变开发调度，不改变完成定义。每种决策仍必须分别记录真实 API 证据、自动
测试、安装态和真机结果；未通过真机的切片必须由 capability/compatibility gate 保持关闭，
不能因其他切片通过而被连带标记完成。

### 11.1 P0.5：扩展前的决策内核收口

P0 真机验收后、P1 增加新决策前，先进行一次不扩大用户功能范围的架构收口：

1. 建立统一 `WorldState`，集中表达角色、牌组、遗物、资源、地图和当前场景；
2. 将状态观察与决策生命周期分开，区分状态快照、决策打开、更新、关闭和 Run 生命周期；
3. 建立通用 `DecisionRequest`，由稳定决策 ID、决策类型、候选、约束和状态引用组成；
4. 建立策略注册机制，让 Card、Route、Shop、Campfire 等策略实现共同接口；
5. 建立通用 `Recommendation`，统一候选身份、排序、适配分、多维评价、数据缺口和版本；
6. 将现有 Card Reward 迁移为第一个策略插件，迁移前后推荐结果和 P0 体验保持兼容；
7. 将左侧面板抽象为统一 `Context Drawer`，P0 仍只渲染 Card Reward；
8. 隔离 Vue、FastAPI 和 RAG 实验入口，避免它们成为实时内核依赖。

P0.5 不重写已验证的真实游戏 API，不改变只读边界，不同时加入新的评分功能。若重构
需要协议升级，必须提供旧 P0 夹具兼容测试和真机回归，不能仅凭代码结构宣告完成。

P0.5 的通用契约还必须满足以下硬约束，未满足前不得开始 P1 策略实现：

1. `event_id` 表示一次不可变观察，`decision_id` 表示一次可跨多次观察更新的稳定决策；
2. 决策打开、更新和关闭必须同时校验 `run_id + decision_id + sequence`，跨 Run 关闭失败
   关闭；同一结果的重复关闭幂等，冲突结果不得覆盖首次结果；
3. 当前检查点只保存一个通用 `current_decision` 及最近关闭防重信息，不得硬编码
   `card_reward`，也不得写入决策历史；
4. 所有实时决策通过统一的 event adapter 构建 `WorldState` 和 `DecisionRequest`，共享策略
   调用、生命周期和 advice envelope，不能为商店、路线或篝火复制完整处理分支；
5. `Recommendation` 的候选必须全部来自请求；跳过、离开等动作只有在真实可用时才作为
   显式候选，通用注册表不得凭决策类型虚构候选；
6. advice envelope 对决策类型保持通用，Card Reward 旧 `advice` 只能作为可选兼容层；
   schema、示例、生产者、消费者和真实实例校验必须同步；
7. `Context Drawer` 的显示、更新和关闭必须绑定决策 handle；旧场景回调不得覆盖或销毁
   新场景抽屉，advice 缺失、错配或失效时必须立即显示 `--` 或隐藏；
8. 自动发布门禁必须执行真实 schema 校验，并让打包 EXE 走过单实例锁和完整初始化路径，
   不能只检查源码字符串或 `--help`。

### 11.2.1 批量扩展的通用候选协议

后续决策不得继续把顶层 `options` 固定为卡牌结构。下一次生产协议只做一次通用候选迁移，
每个候选至少包含：

- `candidate_id`：同一决策内稳定且唯一；
- `kind`：card、relic、potion、service、route_node、rest_action、neow_blessing、
  event_option 等受控枚举；
- `entity_id` 与 `label`：实体稳定 ID 和用户可读名称；没有实体时允许只使用受控动作 ID；
- `eligible` 与结构化不可用原因；
- `cost`：金币、HP、最大 HP、资源或其他明确成本的类型化表示；
- `payload`：按候选 kind 严格校验的最小结构化事实，不能接受任意自由 JSON。

Card Reward 必须迁移到同一候选 envelope，旧 v1-v8 仅用于离线回放。Merchant、Rest Site、
Neow 和 Event 不得在 `realtime.processor` 中各自复制身份、checkpoint、发布或清理代码；
event adapter 只负责把真实 Mod 事实转换为 `WorldState + DecisionRequest`。

跨决策共享一个 `ResourceBudget` 视图，至少表达当前金币、HP/最大 HP、药水槽、牌组大小、
可升级牌、移除收益和路线风险。它是当前状态的确定性派生，不单独持久化历史，也不能把
未来随机奖励当成已知事实。

### 11.2.2 新决策的产品语义

- **Neow**：祝福选择是 `neow_blessing`；祝福随后真正打开的选牌、遗物或其他奖励仍由其
  对应决策类型处理，并以 parent context 标明来源，不能复用上一局或上一屏候选。
- **商店**：卡牌、遗物、药水和移除服务是异构候选；只有游戏真实允许购买的项目可被
  推荐。离开只在原生界面确实允许时作为候选。推荐必须考虑保留金币和同店互斥购买后的
  动态重算，不把“最高 tier”直接等同于购买。
- **篝火**：第一阶段推荐真实可用动作；选择 Smith 等二阶段动作后，再对游戏真实候选
  产生独立子决策。Rest 的治疗量、升级价值和特殊遗物动作只使用当前版本真实 API。
- **事件**：以真实 event/page/option 稳定 ID 为核心。能由静态结构化数据确认的成本收益
  才进入确定性评分；描述不完整、随机结果或版本不匹配时必须降低置信度并报告 data gap，
  不允许 LLM 猜测隐藏结果。

所有候选变化都必须产生同一 decision 的 UPDATED；购买、选择、离开或场景关闭产生
CLOSED。多阶段场景使用显式 parent decision/context，不用 UI 文本或屏幕位置推断。

### 11.3 P1.0：路线完整闭环

P1.0 只实现路线，不同时实现 Neow、商店或篝火。用户体验为：

1. 只有游戏处于“必须从真实下一节点中选择”的状态时才生成路线建议；手动预览地图只
   更新地图观察，不创建伪决策；
2. 策略侧栏显示当前路线模式、真实可选下一节点及推荐度；
3. 独立只读 `RouteMapOverlay` 在真实地图节点之间只显示一条当前主路线；
4. 用户仍由游戏原界面自己点击，Guide 不自动选择、不修改原生绘制内容；
5. 状态、边、候选或视觉锚点不完整时显示 `--` 或隐藏线条，不根据截图坐标补画。

开始 Mod 生产实现前必须从当前本机程序集和真机探针确认：

- 区分“可实际选择下一节点”和“仅打开地图预览”的公开状态；
- 玩家选择真实 `MapPoint` 后的安全 Postfix 触发点；
- 保存继续、切换场景和无选择关闭的时序；
- 地图模型节点与实际 Godot `NMapPoint` 视觉节点的稳定映射；
- 地图滚动，以及视口、分辨率和窗口变化导致的 Godot 全局变换与坐标转换；
- 同一次 origin 选择机会的稳定 identity 来源，以及同 Act 是否可能重访 origin。

找不到这些 API 时任务必须停止并报告，不得用字段名列表、UI 文本、截图位置或宽泛反射
猜测。`NMapScreen.Open` 继续只作为地图观察点，不能单独证明路线决策已经打开。

STS2 `0.108.0` 曾由本机程序集确认不存在用户可操作的地图级 Zoom API；该证据不自动
适用于当前 `0.109.1`。新版本必须重新检查地图拖动、窗口、viewport/content scaling 和
可能新增的 Zoom 行为。Overlay 仍必须对所有真实 transform 变化逐帧重新锚定，不能主动
设置游戏节点 `Scale` 来伪造兼容。

路线决策最初在 schema v6 引入；目标生产发送统一使用 v9，并继续满足：

- 保留既有 `map_choice` 作为地图观察兼容事件；
- 新增 `route_choice`，仅表示真实可操作路线决策；
- `route_choice` 必须包含稳定 `decision_id`、完整 `map_context` 和非空的
  `available_next_node_ids`；
- 路线候选由 event adapter 从真实下一节点 ID 构建，`candidate_id = node_id`，不虚构
  “跳过”或“离开”；
- 选择关闭事件使用同一 `decision_id`，`selected_candidate_id` 为真实节点 ID，并引用最新
  观察 `parent_event_id`；
- 同一当前位置的重复观察产生 `UPDATED`，选择完成后产生 `CLOSED`，新当前位置产生新决策；
- 地图上下文与决策生命周期必须作为两个独立状态变换，在同一次原子 checkpoint 写入中
  一并提交；不能使用互斥 `if/elif` 丢失其中一个，也不能拆成两次写盘暴露中间状态。

`event_id` 每次观察都变化；`decision_id` 必须表示“从同一 origin 选择下一节点”的同一次
机会。当前版本尚未证明同一 Act 内 origin 绝不重访，因此路线使用 Mod 生成的 GUID，并以
Run、Act、真实 origin、规范化候选集合和地图指纹从唯一当前检查点严格恢复；不得使用
RunState/Godot 运行时对象 ID，也不得直接拼接 `{run_id}:route:{act}:{origin}`。Act 初始
可操作地图已有真实 `CurrentMapPoint`（真机样本为 `0:3`），必须使用真实节点；若可操作
界面稳定后 origin 仍为空，则不创建路线决策，不能用 sentinel 伪造。

Recommendation contract v2 在通用候选评价之外增加可选类型化展示数据。当前代码仍
携带历史 `backup_path_node_ids` 兼容字段；PB-2 必须将公开路线展示收口为单条主路线，
旧字段只允许为空或在协议迁移期读取，不得继续绘制第二条路线：

```json
{
  "presentation": {
    "kind": "route_paths",
    "origin_node_id": "0:0",
    "primary_path_node_ids": ["0:1", "1:2", "2:2"],
    "backup_path_node_ids": [],
    "paths": [
      {"candidate_id": "0:1", "node_ids": ["0:1", "1:2", "2:2"], "score": 68.0},
      {"candidate_id": "0:3", "node_ids": ["0:3", "1:4", "2:4"], "score": 61.0}
    ]
  }
}
```

主路线必须从推荐的真实下一节点开始；路径中每一条边都必须存在于当前快照，并最终到达
真实 Boss 节点。Card Reward 在迁移期接受 contract v1/v2，Route 消费者只接受 v2 路线
展示结构。`paths` 仍可按候选 ID 携带内部完整路径行，用于排序和拓扑校验，但地图只渲染
推荐候选的主路径；不确定输出必须让 `recommended_candidate_id` 为 `null`，且路径数组
为空。

路线策略先采用确定、透明、可回放的有界图搜索。输入包括 HP/最大 HP、牌组即时输出、
防御、AOE、成长与资源能力、遗物、药水、金币、节点类型、已知 Boss 和一个版本化默认
风险 profile。PB-2 增加“智能均衡 / 稳健生存 / 激进成长”三种软偏好；路线仍须保留
生存底线，不能把模式实现为节点数量硬约束。
普通怪物与精英只使用房间类型和真实遭遇池的期望风险，不得伪造确定敌人。关键图数据
缺失、Boss 不可达或图不满足已验证约束时，返回空推荐和明确 `data_gaps`。

路线所需的敌人机制、遭遇池和可配置风险常量属于静态结构化事实，进入 SQLite；当前局
地图、当前位置、候选和路径只存在于 `active-run.json`/当前 advice 中，结束后不保存逐次
路线历史。攻略长文和向量索引不进入 P1.0 实时依赖。

`RouteMapOverlay` 只接收节点 ID 和真实边，不接收 Python 计算的屏幕坐标；它绑定当前
`decision_id` 与真实地图 screen owner，`MouseFilter=Ignore`，随地图滚动以及 viewport、
分辨率和窗口变化造成的全局 transform 变化重新定位。
旧界面回调、错配 advice、非法路径或 Drawer 关闭必须清除 Overlay，且不得修改玩家使用
游戏原生绘制/擦除/清除工具产生的内容。

P1.0/PB-2 自动验收至少覆盖 schema v1-v8 回放兼容、v9 生产握手、预览地图不创建决策、
稳定 ID 更新与关闭、跨 Run/过期 parent/非法候选拒绝、真实边与 Boss 可达性、只绘制当前
主路线、确定场景复现、owner-scoped advice 清理、无网络和 P95 不超过 300 ms。真机至少覆盖 Act
初始路线、完成节点后的下一次路线、仅预览地图、选择后清理、地图滚动与窗口/视口变化、
原生绘制不受影响、Route → 战斗 → Card Reward 不残留旧路线，以及保存继续。

协议迁移期可以保留“备选候选排序不同”的内部测试，但 PB-2 的用户界面不得绘制备选线。
路线模式必须在同局保存继续后恢复，新局重置；玩家偏离推荐后以实际节点重算完整剩余路径。

为减少反复启动游戏，PB-2 与 PB-3 可以在自动层连续实施，但不得因此跳过门禁：两者代码
完成后统一进行 `0.109.1` 隔离探针、正式安装和五角色组合真机回归；在组合真机完成前，
TASK-007、PB-2、PB-3 均不能标记为交付完成。

P1.0 明确不做自动选路线、战斗逐回合出牌、普通怪/精英确定身份预测、胜率、RAG/LLM、
自学习、多人模式或未验证 API 的反射 fallback。

### 11.4 推荐模型的演进方向

推荐器内部逐步从“所有信号直接累加成单分”演进为可审计的多维评价：

- 即时战力；
- 生存能力；
- 长期成长；
- 资源效率；
- 牌组负担；
- 机制协同；
- 路线适配；
- 数据完整度与不确定性。

界面仍可显示一个简洁推荐度，但该数值只是当前策略和风险偏好下的排序刻度，不是胜率。
任何新维度都必须有真实输入、上下界、回放场景和负例，不能用更多权重掩盖数据缺失。

### 11.5 开发回放模式

正式产品默认继续遵守“不保存逐决策历史”的数据边界。为支持算法回归和真机问题定位，
允许后续增加显式开启、与正式运行隔离的开发回放模式：

- 默认关闭，不进入公开发行的正常数据流；
- 只在开发者主动开启时记录状态、候选、因子、建议和已确认选择；
- 数据仅保存在本机，可一键清理，不自动上传、不自动训练；
- 回放数据不能混入 `run_summaries`，也不能改变实时推荐；
- 对外发布前必须验证关闭状态不会产生这些记录。

## 12. P2 计划

1. 攻略 RAG：
   - 扩充真正的攻略语料，而不是只有实体解释；
   - 保留原文、来源、语言、版本和章节边界；
   - 长文按标题和语义段落切分，不能只按固定字符截断；
   - 用于用户主动询问“为什么”，不进入实时硬依赖。
2. 可选 LLM 解释：
   - 引用检索证据；
   - 无证据时明确拒绝编造；
   - 网络失败不影响基础推荐。
3. 只读 Strategy Agent：
   - Agent 只在用户主动展开“为什么/替代方案”时运行，不参与 P95 ≤ 300 ms 的实时排序；
   - 输入是冻结的 `WorldState + Recommendation + decision_id`，不能自行重新读取屏幕或猜测
     已变化状态；
   - 工具只允许精确查询 SQLite 实体/机制、读取当前 Recommendation 因子和检索有来源的
     攻略切片；不得调用游戏选择 API、写存档、写当前局状态或访问任意文件；
   - 输出采用 `ExplainResponse`，必须带所解释的候选 ID、关键因子、替代方案、data gaps、
     来源与生成时间；返回前再次校验当前 decision，过期结果不得显示；
   - 没有 LLM、网络超时或攻略库缺失时，退化为确定性因子解释与结构化来源，不影响推荐；
   - Hybrid Search、Reranker、HyDE 或多步规划只有在固定解释评测证明单一检索不足时才能
     启用，不能默认串联所有组件。
4. 个性化：
   - 用户明确开启后只保存聚合偏好；
   - 不默认保存完整决策历史；
   - 与全局推荐规则分层，可随时重置。
5. 在具有足够、合规且按版本隔离的数据后，再评估候选排序模型和胜率模型；
6. 多人模式和跨平台支持最后评估，不属于当前承诺。

## 13. 当前明确不做

- 不自动抓取或分发 Mobalytics、slaythespire-2.com 的内容；
- 不复制 BoberInSpire 代码、权重、流派表或数据；
- 不把大模型放入实时选牌主链路；
- 不把推荐分宣传为胜率；
- 不让 Mod 自动做选择或修改游戏；
- 不在 P0 保存逐事件、逐楼层、逐次选择历史；
- 不在样本不足时做“自我学习”；
- 不为了简历中的 Agent 标签堆叠 Hybrid Search、Reranker、HyDE 等组件；
- 不在地图读取不可信时继续堆路线功能；
- 不把“协议预留”“界面已写”或“代码存在”等同于功能已真机完成。

## 14. 后续决策原则

1. 先保证状态真实，再讨论推荐算法；
2. 默认先完成一个闭环再增加决策类型；批量开发必须共用内核并让每个切片独立门禁；
3. 先保证无网络的确定性基线，再增加 RAG/LLM 解释；
4. 结构化数据走稳定 ID 和关系查询，长文本才走向量检索；
5. 当前局状态短期保存，最终摘要长期保存；
6. 所有外部数据必须有来源、版本、更新时间和可降级策略；
7. 所有推荐都必须能在数据不足或组件故障时安全退出；
8. 游戏 API 必须先通过程序集、真实对象日志或真机回归验证；找不到 API 时安全降级，
   不用字段名、界面文本、截图位置或反射猜测伪造状态；
9. 产品价值来自及时、可靠的局面建议，而不是组件数量。
