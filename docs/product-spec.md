# STS2 Guide 产品规格与实施基线

> 版本：0.1
>
> 决策日期：2026-07-03
> 状态：P0 产品范围已确认，尚未按本规格完成实现

## 1. 文档地位

本文档是 STS2 Guide 后续架构设计、代码改造和验收的产品依据。

- `docs/product-spec.md`：定义“要做什么、为什么做、如何验收”。
- `docs/project-status.md`：只记录某一时点的实现快照，不能反向改变产品范围。
- `protocol/*.schema.json`：定义 Mod 与本地服务之间的机器接口。
- 如果旧文档、当前代码与本文冲突，以本文为准；实现状态必须单独核验，不能把设计目标写成已完成。

## 2. 产品定义

STS2 Guide 是一个面向《Slay the Spire 2》的本地、只读、状态驱动决策 Agent。

用户正常启动游戏，再单独启动 `STS2 Guide.exe`。程序在后台运行，通过只读 Mod
获取当前局面，在选牌界面左侧抽屉显示本地计算的推荐分。用户仍然在游戏中自行操作，
系统不点击、不代打、不修改存档和游戏状态。

P0 的核心不是攻略问答，也不是大模型对话，而是完成一个稳定、低延迟、可解释的
选牌推荐闭环：

```text
游戏状态
  → 只读 Mod 感知
  → 本地 Agent 维护当前局状态
  → 本地规则与数据源计算候选分
  → 游戏内面板显示候选牌和“跳过”的推荐分
```

它仍然属于 Agent 项目，因为系统具备：

1. 感知：监听游戏状态和决策场景；
2. 状态：维护可恢复的当前局检查点；
3. 策略：根据牌组、遗物、路线需求等信号调用本地推荐工具；
4. 行动：主动向用户展示建议；
5. 生命周期：随一局游戏创建、恢复和结束；
6. 扩展工具：以后可按需调用 RAG/LLM 解释“为什么”。

实时 Agent 不以 LLM 为成立条件。P0 不允许网络和大模型成为实时推荐链路的依赖。

## 3. 用户体验

### 3.1 启动

1. 用户正常启动 STS2；
2. 用户启动 `STS2 Guide.exe`；
3. EXE 默认无主窗口，在后台运行；
4. P0 不要求托盘、设置页、历史页、Web 页面或自动启动游戏；
5. P0 只保证当前开发电脑上的单人模式可用。

最终用户不应手动启动 Python、FastAPI、Vite 或终端脚本。Vue 前端不属于 P0
运行依赖。

### 3.2 选牌界面

- 推荐面板由 Mod 创建为 Godot `Control`，锚定游戏原生选牌界面；
- 面板采用贴住视口左边缘的半透明抽屉，宽度根据内容与视口自适应，并设置合理的最小值、最大值和视口占比；
- 抽屉默认展开，点击右缘箭头后向左滑出并仅保留贴边按钮，再次点击滑入；
- 按游戏原始顺序显示实际数量的候选牌名称和“跳过”；
- 每项只显示 `0–100` 的“推荐分”，不显示长解释、置信度或社区分拆；
- 四个分数互相独立，不要求总和为 100，也不表示胜率；
- 最高分项突出显示；
- 数据不足时显示 `--`，不得伪造精确值；
- 选择完成或界面关闭后自动隐藏；
- 除抽屉开关外，面板只显示信息，不覆盖原按钮，不接受替用户做选择的交互。

P0 先以真机效果为准确定间距、字号、颜色和高亮方式，视觉参数不写死为产品约束。
在面板不遮挡原生操作区域的前提下，字号应优先保证窗口模式下的可读性。

## 4. P0 系统架构

```text
┌──────────────────────── STS2 进程 ────────────────────────┐
│                                                           │
│  游戏状态 ──> 只读 C# Mod ──> 临时事件文件                │
│      │                                │                   │
│      └── 原生选牌界面 <── Godot 推荐面板 <── 建议文件      │
│                                                           │
└───────────────────────────────────────────────────────────┘
                                   ▲
                                   │ 本地文件协议
                                   ▼
┌──────────────────── STS2 Guide 后台 EXE ──────────────────┐
│ 协议校验 → 当前局检查点 → 本地推荐器 → 原子写回建议       │
│                    │                                      │
│                    ├── 本地社区先验                        │
│                    ├── 结构化卡牌/遗物数据                 │
│                    └── 当前局状态规则                      │
└───────────────────────────────────────────────────────────┘
                     │
                     ├── 当前局：单一可替换检查点
                     └── 结束后：仅 SQLite 最终结果摘要
```

### 4.1 只读 Mod

负责：

- 读取角色、难度、楼层、生命、金币、能量；
- 读取完整牌组、升级、附魔和负面状态；
- 读取遗物及其动态状态、药水、Run Modifiers；
- 读取选牌候选、候选顺序、是否允许跳过、奖励来源；
- 监听选择、跳过、界面关闭和一局结束；
- 捕获当前节点、地图节点、真实边、可选下一节点和 Boss；
- 将事件原子写入本地目录；
- 读取建议并绘制游戏内面板。

不负责：

- 计算分数；
- 调用网络、LLM 或数据库；
- 修改游戏状态、选项、存档或用户输入；
- 自动点击或代替用户操作。

### 4.2 后台 EXE

负责：

- 启动并托管文件桥接、协议校验、检查点和推荐器；
- 对事件做顺序、重复和过期检查；
- 从本地数据源加载结构化先验；
- 在本机完成评分并原子写回建议；
- 游戏中断后恢复同一局；
- 在胜利、失败或放弃时清理中间状态并保存最终摘要；
- 统一记录本地日志和可诊断错误。

P0 可以由 Python 打包为单一后台 EXE，不要求为了“桌面原生”重写全部推荐逻辑。

### 4.3 Vue、FastAPI、RAG 和 LLM

- Vue 保留为以后攻略问答或历史查看的候选界面，不进入 P0 实时链路；
- FastAPI 可作为开发调试接口保留，但最终 P0 启动不依赖独立 API 进程；
- RAG 只处理攻略语义检索和可选解释，不决定实时分数；
- LLM 以后只能用于用户主动展开的解释，不得阻塞或改变实时基础推荐。

## 5. 数据边界

不同数据按用途存放，不能因为“都能存”就统一塞进向量库或关系库。

| 数据 | 存储 | 生命周期 | 原因 |
|---|---|---|---|
| 卡牌、遗物、角色、版本、来源元数据 | SQLite | 长期 | 稳定 ID、过滤、关联和版本查询 |
| 社区结构化统计 | SQLite（源快照可为 JSON） | 长期 | 数值查询，不需要语义检索 |
| 本地人工整理的 tier 数据 | Git 忽略的 JSON | 用户本机 | 可选私有输入，不随项目分发 |
| 攻略正文和语义切片 | 原文快照 + 向量索引 | 长期、可重建 | 用于 RAG 语义检索 |
| 当前局完整状态 | 单一原子 JSON 检查点 | 当前局 | 需要恢复，不需要历史查询 |
| 待处理事件 | 临时事件队列 | 处理后删除 | 避免快速事件覆盖，不作为历史 |
| 每次选牌分数和选择过程 | 默认不持久化 | 当前决策 | P0 不收集训练样本 |
| 最终对局摘要 | SQLite | 长期 | 战绩查询和以后统计 |

### 5.1 当前局检查点

每一局只维护一个可替换检查点，而不是不断向 SQLite 追加状态历史。

检查点至少包含：

- 可跨游戏重启识别的稳定游戏 Run ID；
- 最近处理的事件序号；
- 当前角色、难度、章节、楼层、生命、金币和能量；
- 当前牌组、遗物、药水、Modifiers；
- 当前节点和已读取的地图快照；
- 当前未关闭决策及其候选；
- 游戏版本，仅用于兼容性诊断。

写入必须使用“临时文件 + 原子替换”。游戏或后台程序异常退出后，只要该局仍可继续，
下次启动就恢复检查点；不能继续或已结束时清理检查点。

当前 Mod 每次启动随机生成的 ID 不能满足恢复要求。P0 必须从游戏可稳定读取的数据
构造或取得 Run ID，并验证不会把两局游戏合并。

### 5.2 最终结果

胜利、失败或放弃后：

1. 写入一条最终结果摘要；
2. 确认写入成功；
3. 删除检查点、临时事件和未完成建议；
4. 不保留逐楼层状态、逐次选牌历史或完整事件流。

最终摘要字段：

- 结果：`win` / `loss` / `abandon`；
- 角色；
- Ascension；
- 最终楼层；
- 最终分数；
- 开始和结束时间；
- 最终牌组；
- 最终遗物；
- 最终药水；
- 游戏版本（内部保留，默认不展示）。

P0 不进行个人习惯学习，也不积累 `decision_outcomes` 训练样本。以后若加入个性化，
优先保存风险偏好、精英路线偏好、牌组精简程度等聚合特征，而不是完整原始对局。

## 6. 本地数据源策略

### 6.1 可随项目使用的数据

- Spire Codex 的结构化实体和社区统计作为默认可重建来源；
- 本项目自己的透明规则、卡牌标签和协同表；
- 经允许发布或项目自行创作的攻略文本。

### 6.2 本机 Mobalytics tier 文件

P0 允许像参考项目一样读取本地 tier 文件，但采用以下边界：

- 数据由开发者在本机人工整理，不编写自动爬虫；
- 建议路径：`data/local/mobalytics_card_tiers.json`；
- 路径加入 `.gitignore`，文件不提交、不打包、不随公开版本分发；
- 只保存推荐所需的卡牌稳定 ID、角色、tier、记录时间和来源地址，不复制网页正文；
- 文件缺失、过期或格式错误时，推荐器必须自动退化到 Spire Codex + 自有规则；
- 使用稳定卡牌 ID 关联，不以中文名、英文名模糊匹配；
- tier 只转为有限权重的基础先验，不能直接决定最终选择；
- 具体 tier 到分数的映射由本项目自行定义和测试，不复制 BoberInSpire 的常量。

建议的最小文件结构：

```json
{
  "schema_version": 1,
  "source": "mobalytics-manual-local",
  "source_url": "https://mobalytics.gg/slay-the-spire-2/tier-lists/cards",
  "captured_at": "2026-07-03T00:00:00+08:00",
  "entries": [
    {
      "card_id": "stable-card-id",
      "character_id": "stable-character-id",
      "tier": "A"
    }
  ]
}
```

这是一项“当前开发电脑优先”的 P0 取舍，不等于将第三方内容纳入项目许可证。
公开发布时默认不依赖该文件。

### 6.3 参考 BoberInSpire 的边界

[BoberInSpire](https://github.com/S0ul3r/BoberInSpire)只用于验证产品链路和理解
“Mod 导出状态 → Python 本地计算 → 覆盖层展示”的可行性。

可以借鉴：

- 本地状态导出和消费的产品思路；
- tier 只作为基础值，再结合当前牌组调整；
- 实时推荐不依赖 LLM。

不得复制：

- 对方代码；
- 对方生成或硬编码的流派表；
- 对方具体权重、tier 分数锚点和数据文件；
- 对方 UI 资源或品牌表达。

本项目的差异化是：游戏内 Godot 面板、稳定 ID、多流派信号并存、正式的跳过候选、
当前局检查点和结束后仅保留摘要。

## 7. 选牌推荐策略

### 7.1 输出定义

每次选牌输出四个同尺度候选：

1. 左侧卡牌；
2. 中间卡牌；
3. 右侧卡牌；
4. 跳过。

推荐分表示“这个选项对当前局面的适合程度”，不是胜率，也不是社区排名。

### 7.2 透明评分原则

P0 使用可追踪的有界加法模型，不把尚未校准的规则包装成概率：

```text
卡牌适配分
  = 50
  + 卡牌基础效果
  + 当前牌组功能缺口
  + 卡牌与牌组协同
  + 当前角色与遗物协同
  + HP、章节和近期路线压力
  + 有界社区先验
```

社区先验只负责在局面信号接近时提供弱排序，不使用固定百分比伪装精度，也不能单独
触发跳过。所有因子必须返回代码、增减值和解释，调权必须通过固定场景集和真机样例
验证，不能因少量个人对局自动学习。

当前局适配至少考虑：

- 卡牌的输出、格挡、抽牌、能量、成长、范围、费用变化和资源代价；
- 当前攻防缺口；
- 能量曲线与出牌负担；
- 抽牌、能量和资源循环；
- 候选与已有卡牌、遗物的协同；
- 章节、Boss 和已知路线对短期能力的需求；
- 升级、附魔和负面状态；
- 重复牌收益或冗余；
- 牌组膨胀代价。

社区高 tier 不能单独强制抓取，社区低 tier 也不能在强协同时被硬性禁止。

卡牌和遗物的效果标签属于结构化事实，写入 SQLite 并由稳定 ID 查询。标签优先从
结构化字段生成，描述规则只作为可版本化、可测试的补充；RAG 和 LLM 不参与实时
标签生成或评分。

路线压力必须按当前可选路径分别统计，再聚合为可达比例和平均风险；不能把互斥分支
上的精英、Boss 和小怪全部视为必经节点。同一威胁对同一候选只能产生一组路线因子，
不得同时叠加“通用危险”和“精英/Boss 危险”。

战前敌人信息必须区分“已知事实”和“遭遇估计”。当前 Act 的 Boss 可以按游戏提供的
稳定身份参与威胁建模；普通怪物和精英在进入战斗前不能被当成已知具体敌人。它们只能
依据当前 Act 的真实遭遇池、已确认的游戏规则和本局已击败精英集合计算候选威胁：
未耗尽的精英池应排除本局已击败精英，池耗尽后才允许出现重复可能。此模型必须输出
候选集合或聚合威胁，不能伪造下一战的确定敌人。

P0/P1 的敌人机制只用于改善选牌和路线的战前风险判断，不提供战斗内逐回合出牌建议。
静态敌人行为与机制可以进入 SQLite；P0 不保存敌人逐回合行动历史。

P0 读取并保留药水状态，但药水是一次性资源，其“提供某种效果”不等于“支持继续
抓取同类卡牌”。在建立经过场景验证的资源替代模型前，药水不参与选牌评分。

自身耗竭、虚无和“与虚无牌交互”必须是不同标签。只有明确区分效果提供者与收益方
后才允许计算协同；无法由当前局状态验证的条件标签只保存事实，不进入实时加分。

### 7.3 多流派并存

P0 不把牌组过早分类为唯一流派。推荐器同时维护多个协同信号：

- 每个信号由已有牌、遗物和资源状态提供证据；
- 证据越强，该信号对候选的影响越大；
- 多个信号可以同时生效；
- 没有足够证据时回到通用攻防、曲线和资源规则。

### 7.4 跳过

跳过是正式第四候选，分数不得固定。它与卡牌使用同一 `0–100` 适配尺度，至少考虑：

- 保持牌组精简的收益；
- 当前牌组大小和重复度；
- 三张候选对牌组造成的冗余或负面影响；
- 当前牌组是否急需补强；
- 当前章节和即将面对的威胁；
- 候选中是否存在明确协同或关键功能牌。

社区先验不能单独把卡牌压到跳过之下。面板高亮必须服从推荐器给出的最终候选，
不得仅对包括不可用“跳过”在内的显示分数取最大值。

## 8. 协议与实时性

### 8.1 事件

P0 实际处理：

- `card_reward`；
- `decision_closed`；
- `run_ended`。

P0 同时正确捕获 `map_snapshot` 所需数据，但不输出路线推荐。商店、篝火、Boss 遗物
等决策事件进入 P1 后再成为推荐工具，不能仅因协议中预留名称就宣称已经支持。

临时事件队列用于避免快速事件互相覆盖。后台确认处理后应删除事件；队列不是审计库。

### 8.2 建议响应

建议协议至少包含：

- 协议版本；
- 对应 Run ID；
- 对应事件 ID；
- 候选稳定 ID 和原始顺序；
- 候选牌与跳过的推荐分；
- 最高分候选；
- 生成时间；
- 推荐器版本；
- 数据不足或降级标记。

Mod 必须拒绝显示属于旧事件、旧 Run 或候选不匹配的建议，避免“上一组牌的分数”
显示在下一组选项旁。

### 8.3 性能目标

- 实时推荐不访问网络；
- 本地事件被发现到建议文件写回的 P95 不超过 300 ms；
- 单次纯评分应明显低于总预算，并通过基准测试记录；
- 数据源加载在后台启动时完成，不能每次选牌重新解析全部文件；
- 推荐器异常时游戏继续正常运行，面板显示 `--` 或隐藏。

## 9. 路线能力边界

P0 只做正确采集，不做路线推荐。

必须采集：

- 当前节点；
- 完整节点列表；
- 节点类型和坐标；
- 游戏提供的真实连边；
- 当前可到达的下一节点；
- 当前 Act 的 Boss。

进入具体战斗前，地图节点只能说明普通战、精英或 Boss 类型。除已知 Boss 外，不得把
普通怪物或精英预测成某个确定敌人；后续威胁模型只能基于遭遇池和已击败精英排除规则
计算期望风险。

禁止：

- 读取失败时伪造“下一行全部相连”；
- 用猜测边运行推荐器；
- 在前端展示看似可用的三种路线策略；
- 将地图界面打开等同于地图数据已正确读取。

路线推荐在 P1 使用经过回放和真机验证的图数据实现，并与生命、牌组、遗物和章节需求联动。

   - 显示下一节点建议，不自动选择。
2. Boss 遗物、商店、篝火和药水决策；
3. 托盘、设置、日志导出和状态诊断；

7. 为公开发布切换到可分发数据源，不携带本机 Mobalytics 文件。

P1 每增加一种决策，都必须具备：真实状态捕获、建议协议、确定性基线、游戏内展示、

## 12. P2 计划

1. 攻略 RAG：
   - 扩充真正的攻略语料，而不是只有实体解释；
   - 保留原文、来源、语言、版本和章节边界；
   - 长文按标题和语义段落切分，不能只按固定字符截断；
   - 用于用户主动询问“为什么”，不进入实时硬依赖。
2. 可选 LLM 解释：
   - 引用检索证据；
   - 无证据时明确拒绝编造；
   - 网络失败不影响基础推荐。
3. 个性化：
   - 用户明确开启后只保存聚合偏好；
   - 不默认保存完整决策历史；
   - 与全局推荐规则分层，可随时重置。
4. 在具有足够、合规且按版本隔离的数据后，再评估候选排序模型和胜率模型；
5. 多人模式和跨平台支持最后评估，不属于当前承诺。

## 13. 当前明确不做

- 不自动抓取或分发 Mobalytics、slaythespire-2.com 的内容；
- 不复制 BoberInSpire 代码、权重、流派表或数据；
- 不把大模型放入实时选牌主链路；
- 不把推荐分宣传为胜率；
- 不让 Mod 自动做选择或修改游戏；
- 不在 P0 保存逐事件、逐楼层、逐次选择历史；
- 不在样本不足时做“自我学习”；
- 不为了简历中的 Agent 标签堆叠 Hybrid Search、Reranker、HyDE 等组件；
- 不在地图读取不可信时继续堆路线功能；
- 不把“协议预留”“界面已写”或“代码存在”等同于功能已真机完成。

## 14. 后续决策原则

1. 先保证状态真实，再讨论推荐算法；
2. 先完成一个闭环，再增加决策类型；
3. 先保证无网络的确定性基线，再增加 RAG/LLM 解释；
4. 结构化数据走稳定 ID 和关系查询，长文本才走向量检索；
5. 当前局状态短期保存，最终摘要长期保存；
6. 所有外部数据必须有来源、版本、更新时间和可降级策略；
7. 所有推荐都必须能在数据不足或组件故障时安全退出；
8. 产品价值来自及时、可靠的局面建议，而不是组件数量。
