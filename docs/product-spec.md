## 2. 产品定义

STS2 Guide 是一个面向《Slay the Spire 2》的本地、只读、状态驱动决策 Agent。

用户正常启动游戏，再单独启动 `STS2 Guide.exe`。程序在后台运行，通过只读 Mod
获取当前局面，在选牌界面左侧抽屉显示本地计算的推荐分。用户仍然在游戏中自行操作，
系统不点击、不代打、不修改存档和游戏状态。

P0 的核心不是攻略问答，也不是大模型对话，而是完成一个稳定、低延迟、可解释的
选牌推荐闭环：

```text
游戏状态
  → 只读 Mod 感知
  → 本地 Agent 维护当前局状态
  → 本地规则与数据源计算候选分
  → 游戏内面板显示候选牌和“跳过”的推荐分
```

它仍然属于 Agent 项目，因为系统具备：

1. 感知：监听游戏状态和决策场景；
2. 状态：维护可恢复的当前局检查点；
3. 策略：根据牌组、遗物、路线需求等信号调用本地推荐工具；
4. 行动：主动向用户展示建议；
5. 生命周期：随一局游戏创建、恢复和结束；
6. 扩展工具：以后可按需调用 RAG/LLM 解释“为什么”。

实时 Agent 不以 LLM 为成立条件。P0 不允许网络和大模型成为实时推荐链路的依赖。

首个公开版本不是“当前开发电脑能运行”的同义词，而是 Windows Public Beta。它的明确
支持范围为：

- Windows、STS2 单人模式和安装包兼容清单中列出的精确游戏版本；
- 原版五个角色全部可用，不以只完成铁甲战士作为公开发布门槛；
- 用户能力冻结为选牌建议与路线建议，Neow、商店、篝火和其他决策后续迭代；
- 原版内容加 STS2 Guide 自己的只读 Mod；其他玩法型、内容型 Mod 不属于首版兼容承诺；
- 实时推荐完全本地运行，默认不上传遥测、牌组、存档或局内事件。

“当前版本”必须由发行兼容清单精确表达，不能写成永久范围。游戏升级后必须重新核对
程序集/API、协议、静态数据、自动测试和对应真机证据，不能沿用旧版本的验收结论。
版本不匹配必须停止推荐；本机实际版本与验证快照见项目状态，不在产品范围中固定历史版本。

### 2.1 求职演示交付里程碑（2026-09-11，后续开发安排由 2.3 节覆盖）

交付一版能够现场运行、能够解释关键设计的 STS2 Guide。此阶段优先级覆盖下文历史
扩展排期；保留五角色选牌和单路线的既有范围，商店、篝火、Neow、事件与 Deck Edit
暂缓，未验收能力继续关闭。

2026-09-22 确认本阶段交付对象：以用户求职现场演示为主，同时完成少量其他玩家的
独立安装与使用试验，暂不公开发布。试装用于验证离开开发电脑后能否按 README 使用，
不等于承诺大范围兼容。试装规模为 2–3 位使用受支持游戏版本的 Windows 单人玩家，
各自依据 README 完成安装启动、获得正确候选的选牌建议与路线、保存退出并继续、
关闭游戏后后台正常待机。不依赖开发环境，不要求打完整局或证明胜率提升。
若必须由开发者远程改配置、补文件才能运行，应记录问题并修复复测，不能算独立试装通过。
2026-09-23 本轮范围与验收讨论已收口，实施规格见第 2.2 节。本次 to-spec 仅交付规格与
待实现任务，不代表已实施、已验收或授权本轮启动安装和游戏操作。

2026-09-22 确认建议不可用时的体验：

- 已支持的选牌或路线决策中，没有有效分数时保留抽屉，显示 `--` 与简短状态说明；
  区分等待结果、必要数据不足和建议暂不可用，不把 `--` 当作零分或跳过建议。
- 原因必须有可验证依据；仅凭没有建议文件不能断言 Host 未启动，无法确定时显示
  “建议暂不可用”，不得猜测原因。恢复有效结果后自动恢复展示。
- 等待或异常期间清除失效分数、高亮与路线，不显示上一局、上一屏或不匹配候选的建议。
- 未支持的 Neow、商店等决策静默隐藏；版本不匹配时停止推荐，由托盘说明原因，
  不用弹窗打断游戏。本规则优先于历史 P0 对未支持场景“隐藏或显示 `--`”的宽松约定。
- 可选数据缺失但仍有有效评分时，不一律改成 `--`；不得借显示调整改变既有评分语义。

按以下顺序完成：

1. **当前版本可用**：读取本机 Steam 游戏的实际版本，核对所用 API 与静态数据，修复已
   证实的兼容问题。旧版本测试和真机记录仅作历史依据；当前版本实际运行通过后才宣称支持。
2. **普通玩家流程顺畅**：从最终安装包完成安装、从 Steam 启动游戏、启动 Guide、获得
   选牌与路线建议、保存退出并继续。清除错候选、旧建议、无法恢复和残留 Worker 等卡点；
   用户不需要 Python 环境、终端命令或测试 Mod。
3. **可展示且可解释**：提供一段真实简短演示，以及清楚的 README。演示覆盖真实选牌、
   路线和保存继续；README 说明安装运行、支持范围、状态与决策流、SQLite 与可选 RAG
   的职责、本地评分的取舍和已知限制。材料中的版本和功能必须与演示安装包一致。

本阶段以可复现的使用结果为验收依据，沿用必要验证，不增加与演示交付无关的校验框架。
不以只修改版本白名单、脚本回放或视频剪辑替代当前版本真实流程验证。

2026-09-22 确认阶段结束标准，分开记录两个节点：

1. **提交用户验收**：当前支持版本的五角色选牌、路线、保存继续和后台生命周期完成
   对应验证，已发现的范围内阻断问题修复并复测，独立审查无阻断；交付同一版本的
   安装包、README、真实演示和已知限制清单。达到此节点停止扩展功能。
2. **阶段完成**：用户验收通过，且 2–3 位玩家完成上述独立试装。此期间只修复阻碍
   既定使用流程的问题，权重优化与新功能留到下一阶段。试装人员尚未到位时，准确
   标记“本机验收通过，独立试装待完成”，不虚称阶段完成，也不因此无限增加开发范围。

静态来源更新不得覆盖 Guide 自有策略参数。路线风险参数独立维护于
`data/guide_mechanics.json`，构建知识快照时显式合并并标注本项目来源，再进入 SQLite；
运行时仍从发行 SQLite 读取，不新增网络依赖或静默默认值。

**工程正确性与推荐质量分别表述**：自动测试证明协议、生命周期及确定性规则等行为，
不证明胜率提升或推荐策略优秀。推荐分始终是局面适合度。

2026-09-22 确认本阶段推荐质量底线：修复范围内已发现的明确数据和逻辑错误，包括
实体 ID 不匹配导致已持有的药水/遗物未参与既有评分、失效建议、无法到达的推荐路线，
以及建议理由引用当前局不存在的事实。允许评分权重暂不成熟，不要求每次排序符合高手
偏好，不承诺最优解或提高胜率。暂未建模的机制须明确记录限制；不得将读取/映射缺陷
冒充策略限制，也不得通过调权重掩盖数据错误。

上述交付完成后，如继续投入，
优先抽查少量真实局面的推荐及理由是否合理，记录反例和数据缺口；这属于后续质量评估，
不扩大实时历史持久化、不做自学习，也不设为本轮必须完成的大型评测工程。

### 2.2 求职演示版实施规格（to-spec，2026-09-23）

本节将第 2.1 节已确认的取舍转为可执行规格，不扩大阶段范围。具体文件定位、实施顺序
和验收清单由 TASK-013 承接；当前完成度仍以实际证据为准。

#### Problem Statement — 用户问题

现有候选已经具备实时选牌、路线和 Windows 交付框架，但实体身份映射存在缺口，可能
导致已持有的资源漏算；建议不可用时只有 `--`，用户无法区分等待与异常。当前版本的
五角色与独立安装证据尚不完整，旧文档又混杂历史状态，因此还不能作为可信的求职演示版。

#### Solution — 本阶段方案

保留现有本地只读架构，把真实状态正确连接到推荐与界面，并让等待、不可用和恢复行为
可理解。先完成最终安装包上的验证，再交付清楚的使用说明、真实演示与已知限制。
不通过增加新决策或大模型补偿基础可靠性问题。

#### User Stories — 用户故事

1. 作为试装玩家，我希望按说明安装，不配置 Python、终端或开发工具，以便独立开始使用。
2. 作为玩家，我希望正常从 Steam 启动游戏，并能先开游戏或先开 Guide，以便保持自己的习惯。
3. 作为玩家，我希望重复打开 Guide 不会多开后台，以免出现多份建议或残留进程。
4. 作为玩家，我希望明确知道支持的游戏版本和单人范围，以免将不兼容误认为推荐故障。
5. 作为五个原版角色的玩家，我希望各角色都经过相应验证，以免通用内核可用被误称为全角色支持。
6. 作为选牌玩家，我希望候选名称、顺序和跳过资格与当前游戏一致，以免参考错误选项。
7. 作为玩家，我希望已经读取的牌组、遗物、药水和局面正确进入既有策略，以免因 ID 错误漏算资源。
8. 作为玩家，我希望推荐分表示本次决策的局面适合度，而非胜率或跨局通用强度，以便正确理解建议。
9. 作为玩家，我希望等待或无法评分时看到简短、诚实的说明，以便知道建议暂时不可用。
10. 作为玩家，我希望异常、换局或候选变化时清除失效建议，并在恢复后自动更新，以免看到旧结果。
11. 作为玩家，我希望进入未支持场景时界面安静隐藏，以免误以为商店或 Neow 已受支持。
12. 作为选路玩家，我希望在三个软偏好中选择，并只看到一条真实可达路线，以便快速参考。
13. 作为选路玩家，我希望偏离建议后按实际位置重算、地图滚动和窗口改变后仍对齐，以便继续自主操作。
14. 作为玩家，我希望保存继续遵循游戏实际恢复位置，并正确恢复建议和路线偏好，以免复用离开前的错误状态。
15. 作为玩家，我希望关闭游戏后后台待机，完全退出 Guide 后结束后台任务，以便控制资源占用。
16. 作为玩家，我希望版本不兼容时停止推荐并由托盘说明，不用弹窗打断游戏，以便安全处理更新。
17. 作为求职演示者，我希望安装包、README、演示和限制清单一致，以便现场展示并解释真实设计。
18. 作为试装玩家，我希望不必把存档或逐局事件上传给开发者，也不依赖开发者补文件才能使用，以便验证独立可用性。
19. 作为项目负责人，我希望明确区分本机验收和外部试装，以便在达到约定标准后停止本阶段开发。

#### Implementation Decisions — 实施决定

- **沿用已有模块**：保留只读观察器、完整世界状态、统一决策生命周期、策略注册表、
  本地结构化目录、抽屉、地图覆盖层及托盘控制器。不重建并行推荐链路。
- **稳定身份**：真实游戏模型的稳定身份是目录连接依据，使用已由当前本机程序集验证
  的成员。逐一核对范围内读取入口，不从类名剥后缀猜 ID，不用模糊匹配或零散别名掩盖问题。
  ID 与候选身份用途分开；修复不能破坏当前决策匹配和候选顺序。
- **事实与策略分开**：修复漏读、错误映射和不存在事实的理由；仍未建模的复杂机制登记为
  限制。沿用现有权重，不增加逐回合模拟、胜率模型或通用权重调优工程。
- **统一状态展示**：选牌和路线共用抽屉的简短状态语义，不各自发展一套故障界面。
  有效分数正常显示；等待当前结果时显示占位及等待提示；有明确必要数据缺失时说明
  数据不足；其余无法确定原因时只说建议暂不可用。空分数不等于零分或跳过建议。
- **状态与连接分开**：当前建议是否匹配真实决策，与后台是否活跃是不同事实。正常静止
  的决策不能只因文件变旧被判为过期；文件存在也不能证明后台存活。先复现异常退出后的
  残留路径，再复用现有控制器/状态通知作最小修复，不引入通用监控服务。
  后台失联或结果失效时撤下分数、高亮和路线，恢复后仅接纳当前局面匹配的建议。
- **不猜原因**：只有确有依据才显示“后台未启动/已断开”等具体原因；仅凭建议文件缺失
  不足以区分未启动、计算中和读取失败。记录检测周期与可验证的失联检测上限，测试覆盖
  上限内的状态切换；不新增面向用户的复杂超时配置。
- **保留边界**：版本不匹配停止推荐，托盘说明；未支持场景静默隐藏。可选数据缺失但
  仍有有效评分不一律变成空分数。本阶段不增加常驻解释栏、聊天入口或新面板。
- **协议最小变更**：优先复用现有结果元数据与运行状态。确需增加跨进程状态字段时，先
  定义唯一契约，同步版本、示例、生产者、消费者和测试；不得只改界面而猜测后台事实。
  不以提示功能扩大当前局历史存储，不增加遥测或网络依赖。
- **恢复与发行**：同一局按真实游戏恢复状态重建建议；新局或结束不继承旧候选和偏好。
  修复后用同一最终发行产物验证，开发构建、安装态和运行态分别记录。
  保存回主菜单关闭的是当前可观察决策，不是结束整局：撤下建议、保留当前局检查点和
  路线偏好；继续游戏时按实际恢复界面重建决策，不伪造跳过、选择或最终战绩。
  选牌等待/离线占位的名称来自已校验匹配的当前屏幕卡牌模型，不能依赖建议文件才能
  显示本地化牌名；屏幕替换时清空名称，避免串用上一屏。
- **有限清理**：修正与当前交付矛盾的描述，历史证据标明对应版本。测试不按年代删除；
  仅在确认行为已被替代后调整断言并保留有效覆盖，不借此开展全仓重构。

#### Testing Decisions — 测试决定

测试关注可观察的输入输出与生命周期，不以方法名、代码行数、测试总数或实现细节作为
成功标准。优先复用现有接口；只在必须执行跨语言真实边界时增加最小验证入口。

| 测试边界 | 主要验证内容 | 既有基础与限制 |
|---|---|---|
| 数据 → 建议 | 游戏稳定 ID 进入发行目录，资源贡献不漏算，候选与路线真实合法，理由只引用已有事实 | 沿用发行数据库、当前目录、选牌和路线策略测试；补真实生产映射覆盖，不只测试手写规范 ID |
| 事件 → 展示 | 首次等待、错误身份、损坏结果、数据不足、关闭/换局、后台退出与恢复，不残留旧分数或路线 | 沿用文件桥、生命周期、Controller 测试；源码契约仅辅助，Godot 回调与显示须真机 |
| 安装包 → 用户流程 | 安装向导、双启动顺序、重复启动、五角色、保存继续、偏离路线、地图适配、待机和完全退出 | 沿用发行构建/审计与真机流程；无开发环境的独立试装不能用本机测试替代 |

每个已复现缺陷先留失败证据或回归，再实现修复并复测；自动测试须覆盖有效结果不被
误清除的正例。全量 Python、Mod/PCK 编译与最终包构建均需通过，代码及自动验证交付后
由独立角色审查。五角色仍需通用规则、角色机制和当前版本第一幕对应真机证据。

### 2.8 选牌评分内核 v2：牌组适合度（2026-10-01，TASK-025）

依据 2026-10-01 grill 结论与 [`adr/0001-deck-fitness-scoring.md`](adr/0001-deck-fitness-scoring.md)；
术语见仓库根目录 `GLOSSARY.md`。本节是第 2.7 节在制上限下唯一的在制任务；切换完成后，
第 7.2 节的加法模型与社区先验、第 7.4 节的独立跳过公式由本节取代，其余第 7 节约束继续有效。

#### Problem Statement

0.3.11 真机（IRONCLAD）中，挑衅因“当前遗物支持该牌的技能、格挡效果”获得 +4 并排第一，
但战纹涂料只在拾起时升级技能牌，斗篷扣按回合结束时的手牌数给格挡，都不支持这张牌；
同屏跳过分又明显偏低。追查发现问题不在个别数值：发行库中全部遗物“支持”标签和大部分
卡牌效果标签来自描述文字匹配；评分是“50 分加几十条独立加减规则”，各规则量纲不统一、
存在阈值断崖、同一事实被多条规则重复计分，跳过另有一套公式，也没有牌组稀释。玩家看到
的理由可能引用不存在的事实，排序无法用一个一致的原理解释。

#### Solution

选牌的每个选项（三张卡牌与跳过）都评为“做出该选择后”的**牌组适合度**，显示为
`100 × 适合度`、保留 1 位小数。适合度比较两件事：牌组在各**能力维度**上的能力（每张牌按
抽到概率与能量上限折算），以及由幕、层数、推荐路线、已知 Boss、生命值和偏好决定的
**局面需求**。拿一张牌会带来贡献也会稀释循环，跳过因此是算出来的，小卡组循环的收益
自然体现。卡牌与遗物的机制只来自当前游戏程序集核对过的事实，全部卡牌与遗物覆盖后才
替换旧版本；替换前用**标准答案集**证明新版不劣于旧版。评分不再使用社区先验。

#### User Stories

1. 作为玩家，我希望每个选项的分数表示“选了之后牌组整体有多适合当前局面”，以便直接比较卡牌与跳过。
2. 作为玩家，我希望跳过的分数是根据当前牌组算出来的，以便在小卡组循环更好时看到跳过领先。
3. 作为玩家，我希望拿一张边际价值低的牌时看到它因稀释循环而低于跳过，以便避免牌组膨胀。
4. 作为玩家，我希望分数保留 1 位小数，以便区分单张牌对整副牌组的细小影响。
5. 作为玩家，我希望牌组缺少防御时防御牌价值明显上升，而防御已足够时再拿防御牌价值很低，以便建议体现真实缺口。
6. 作为玩家，我希望下一段推荐路线上的精英、篝火和本幕 Boss 会影响需求，以便选牌为接下来的战斗做准备。
7. 作为玩家，我希望切换路线模式后，选牌所依据的路线需求随之改变，以便路线与选牌逻辑一致。
8. 作为玩家，我希望生命值很低时生存相关需求上调，以便建议不忽视当前风险。
9. 作为玩家，我希望已知 Boss 的威胁（如高群伤或高攻击压力）进入需求，以便提前补足对应能力。
10. 作为玩家，我希望我的高级偏好（生存、即时输出、长期成长）调整需求权重，配置方式和范围不变，以便沿用原来的习惯。
11. 作为玩家，我希望角色引擎（耗竭、力量、弃牌、小刀、中毒等）按提供者出现频率与收益方强度折算成通用能力，以便协同不被重复计分。
12. 作为玩家，我希望遗物只在程序集证实的情况下参与评分，以便不再看到“遗物支持”却实际无关的理由。
13. 作为玩家，我希望直接改变牌组能力的遗物（如每回合额外能量）改变牌组基线，以便所有选项在正确的起点上比较。
14. 作为玩家，我希望在特定卡牌或动作时生效的遗物让相关卡牌更有价值，以便真实的遗物协同得到体现。
15. 作为玩家，我希望只在拾起时生效或与出牌无关的遗物不影响选牌，以便理由不引用无关遗物。
16. 作为玩家，我希望会因跳过而获得收益的遗物提高跳过的适合度，以便跳过的真实收益被计入。
17. 作为玩家，我希望确定性的特殊效果（如下一张攻击免费）被换算为对应能力的期望值，以便这类牌不被低估。
18. 作为玩家，我希望随机效果按游戏规则的已知分布计算期望，以便评分不因随机性被跳过。
19. 作为玩家，我希望条件效果按牌组与路线估算成立概率，以便条件牌得到合理估值。
20. 作为玩家，我希望真正无法在选牌时得知的部分被明确说明，以便知道评分的边界。
21. 作为玩家，我希望升级、附魔、苦痛按结构化数据计入，以便同名不同状态的牌得到不同评价。
22. 作为玩家，我希望诅咒、状态等负面牌对循环的拖累被计入，以便牌组已有负面牌时建议仍然准确。
23. 作为玩家，我希望遇到不认识的候选牌时显示 `--` 与“数据不足”，而不是一个猜测的分数。
24. 作为玩家，我希望牌组里有不认识的牌或遗物时其余选项仍可评分，并提示置信度降低。
25. 作为玩家，我希望展开“评分依据”时看到对该选项贡献最大的能力维度，并点名涉及的具体卡牌与遗物，以便在游戏里核对。
26. 作为玩家，我希望未建模或无法得知的说明优先展示，以便先看到评分边界。
27. 作为玩家，我希望抽屉的布局、交互和出现时机不变，以便新评分不增加学习成本。
28. 作为玩家，我希望所有分数只来自当前局面的计算，不掺杂别人的胜率统计，以便理由都能用局面解释。
29. 作为玩家，我希望五个角色使用同一套评分原理，以便切换角色时理解方式一致。
30. 作为开发者，我希望每张卡牌、每件遗物的机制事实带有程序集方法级来源并锁定该类自身的代码指纹，以便游戏更新后只有代码改动过的条目失效、需要重审，而不是被悄悄套用或全部作废。
31. 作为开发者，我希望一个只读提取工具按钩子结构把遗物初步分为基线、触发与无关三类，以便人工审核只集中在少数复杂遗物上。
32. 作为开发者，我希望同一工具导出卡牌出牌效果所调用的游戏命令，以便简单效果自动确认、复杂效果进入人工审核。
33. 作为开发者，我希望覆盖率检查要求全部卡牌与遗物都处于“已换算”或“已登记无法得知”，以便不存在“没看过”的效果。
34. 作为开发者，我希望描述文字匹配不再产生进入评分的机制标签，以便事实来源唯一。
35. 作为开发者，我希望能用真实对局快照在同一策略入口上同时运行新旧版本，以便比较质量。
36. 作为开发者，我希望标准答案集记录每个局面的“最佳选择”和“明显错误”，以便用最佳选择命中率与明显错误次数衡量版本。
37. 作为开发者，我希望只有新版命中率不低于旧版、明显错误排第一为 0 且完整测试通过时才切换，以便切换有客观门槛。
38. 作为开发者，我希望局面需求参数属于 Guide 自有参数并标注来源，以便调参可追溯且不被静态数据更新覆盖。
39. 作为开发者，我希望新版作为新的选牌策略版本接入现有策略注册表，旧版保留为回退，以便切换与回退都不改协议。
40. 作为开发者，我希望发行指纹与兼容清单反映新的策略、标签与数据版本，以便新旧组件不会混用。
41. 作为产品负责人，我希望演示时能说明“所有分数来自局面因果计算、机制来自程序集事实、质量有标准答案集指标”，以便清楚解释设计取舍。
42. 作为试装玩家，我希望新版不改变安装、启动、托盘和保存继续的使用方式，以便试装流程不受影响。

#### Implementation Decisions

- **能力维度**固定为前期输出、群伤、防御、成长、循环、能量六项。角色引擎与触发遗物不另设需求，
  按“提供者出现频率 × 收益方强度”折算进这六项。
- 每张牌的贡献按解析期望计算：每回合抽到概率约为手牌数除以牌组张数，并受每回合能量上限约束；
  不做蒙特卡洛模拟。牌组越大单张贡献越低，稀释自然体现。
- **局面需求**由幕、层数、当前路线模式下推荐路线从当前位置到本幕 Boss 的节点、已知 Boss 威胁、
  生命值共同决定；拿不到推荐路线时退回按可达路径比例估计。需求参数属于 Guide 自有参数，与现有
  路线风险参数放在同一处，构建时并入发行 SQLite 并标注本项目来源。
- 高级偏好改为作用在需求权重：生存对应防御，即时输出对应前期输出与群伤，长期成长对应成长与循环；
  文件格式、范围 0.75–1.25、非法回默认、需重启生效的规则不变。
- **牌组适合度**为各维度满足度的加权和，收益递减，缺口惩罚陡于富余奖励；显示为 `100 × 适合度`、
  1 位小数。跳过的分数为当前牌组（含跳过时触发的遗物收益）的适合度，不固定。
- 不再使用 Spire Codex 社区先验与本机 Mobalytics tier；两者的数据仍可保留在库中，但不进入评分。
- 遗物分为**基线遗物**、**触发遗物**、**无关遗物**。基线遗物进入牌组能力基线；触发遗物作为交互项
  提高相关卡牌价值；无关遗物不参与选牌评分。
- 效果建模标准：确定效果换算为期望值；随机效果按游戏规则的已知分布求期望；条件效果按牌组和路线
  估算成立概率（取代第 7.2 节“条件标签不进入实时加分”的旧约束）；只有选牌时真正无法得知的部分
  登记为缺口并给出说明。升级、附魔、苦痛按结构化数据计算，缺数据时登记缺口。
- 卡牌与遗物机制事实只来自当前本机游戏程序集的只读元数据/IL 核对，每条事实带类型、成员、token
  来源，并锁定该卡牌/遗物类自身（含其嵌套状态机与匿名方法）的代码指纹；指纹不符时该条事实
  失效、按未知处理，未改动的条目继续有效。整个程序集 SHA256 仍只用于兼容清单判断已知游戏版本。
  开发时可由审核 Agent 起草复杂效果的解读；确认方式（2026-10-02 用户决定）为另一独立 Agent 对照 IL 逐条交叉复核，
  分歧由开发者依据 IL 裁决并在证据中写明，用户在真机中抽查；未经交叉复核的事实不得计入切换门槛；Spire Codex 结构化字段只用于
  交叉核对，与程序集结论冲突时标记重审，不作为评分来源。描述文字匹配不再产生进入评分的机制
  标签。只读提取工具属于开发工具，不进入产品或发行包，不实例化游戏模型、不执行游戏方法。
- 覆盖范围为发行库全部 595 张牌（五角色、无色、事件、诅咒、状态、衍生、任务、远古）与全部遗物类；
  全部覆盖前不切换。
- 不认识的候选牌不给分、显示 `--` 与“数据不足”，不参与推荐排序；牌组中不认识的牌只计入稀释、
  不认识的遗物不参与，均登记缺口并降低置信度，其余选项照常出分。
- 依据因子为各能力维度对该选项适合度的贡献，按绝对值排序，点名涉及的具体卡牌与遗物；未建模/
  无法得知说明优先；抽屉最多 3 条的规则不变。
- 新版作为新的选牌策略版本注册到现有策略注册表，旧版保留为回退；协议 schema 不变，抽屉仅将分数
  改为 1 位小数显示。Guide/Mod/policy/SQLite 版本与发行指纹、兼容清单同步更新。
- 路线、商店、篝火、Neow、事件评分不在本次改动；商店等仍为 pending_validation 并关闭。

#### Testing Decisions

- 好的测试只验证对外行为：给定真实局面，输出的分数、跳过、排序、依据、缺口和置信度是否正确；
  不测试维度计算、需求函数、抽到概率等内部实现，重构内部时测试不需要改动。
- **主接缝**：用 `WorldState` 与 `DecisionRequest` 通过策略注册表调用选牌策略，得到 `Recommendation`，
  数据来自真实构建的发行 SQLite。沿用现有“构建发行库 + 公共策略入口”的回归方式。先写失败测试：
  战纹涂料、斗篷扣不产生遗物协同；小卡组中边际牌低于跳过；不认识的候选显示 `--`；偏好只作用一次。
- **标准答案集评估**在同一主接缝上运行：真实快照转换为 `WorldState`，新旧版本分别输出，统计最佳
  选择命中率与明显错误排第一次数；局面由开发者起草、用户修订，覆盖五个角色。
- **事实数据接缝**：发行库构建测试检查按类指纹不符时该条事实失效、覆盖率 100%、无描述文字来源的
  评分标签。
- **Mod 显示接缝**：沿用现有 C# 行为测试，只验证分数 1 位小数显示与依据优先顺序。
- 完整 Python 测试、Mod/PCK 编译、候选构建后，才进入五角色安装态真机；真机仍按第 2.7 节清单执行。

#### Out of Scope

- 路线、商店、篝火、Neow、事件、删牌的评分改造与能力开启；统一估值复用到这些决策留待后续。
- 战斗模拟（蒙特卡洛对战、战斗内逐回合出牌）、敌人下一招预测、胜率预测。未来选牌奖励的抽样见下方
  “前瞻”补充，它只对奖励出牌池抽样，不模拟战斗。
- 从对局自动学习权重或收集训练样本；需求参数只由人工设定并用标准答案集检验。
- 协议 schema 与抽屉布局的结构性改动。
- 社区先验以任何形式参与评分。

#### Further Notes

- 选择“全部覆盖后再切换”意味着演示与五角色真机验收推迟到切换之后；0.3.11 已通过的生命周期项
  在新版上需要复测，不直接继承。
- 开发期间用户用 0.3.11 继续游玩其余角色，记录器保存选牌局面作为标准答案集来源，并顺带完成
  不依赖评分的生命周期检查。
- 推荐分仍表示当前局面适合度，不是胜率；1 位小数不代表更高的预测精度，只用于区分细小差异。

#### 补充：前瞻与协同说明（2026-10-09，用户决定）

背景：38 个已确认局面上，v2 的整体排序（标准答案平均名次 2.24、前两名 26 次）已略好于 v1
（2.29、22 次），但第一名命中仍低（11 对 15）。失误集中在用户为流派铺路的选择（例如 SILENT 第 2 层
选早有准备）：v2 只评“当前牌组”，不计尚未拿到的牌。

决定：

1. **前瞻**：候选的分数改为本幕剩余战斗上的牌组适合度平均。拿下候选后，按推荐路线上的每场战斗
   依次出现选牌奖励；奖励从角色卡池按程序集中的稀有度机率抽 3 张不重复的牌
   （`CardRarityOdds`：一般战斗普通 60%／罕见 37%／稀有 3%，精英 50%／40%／10%，Boss 必稀有；
   进阶 7 起为 61.5%／37%／1.49% 与 54.9%／40%／5%——`GetValueIfAscension(等级, 进阶值, 基础值)` 的第一个数是进阶值；
   稀有保底偏移按初始值 −5% 计，实际偏移属于存档状态，未知时不猜），
   模拟玩家在 3 张与跳过中按同一适合度贪婪选择。
   - 抽样只针对奖励，不模拟战斗；所有候选共用同一组抽样情境，随机种子由决策 ID 决定，结果可重现。
   - 卡池为该角色普通／罕见／稀有牌，排除仅限多人的牌；稀有度来自卡牌构造函数，已与目录逐张核对一致。
   - 预算：情境数与前瞻奖励数为参数（初始 8 个情境、最多 4 次奖励），须保持实时 P95 ≤ 300 ms。
   - 本幕已无剩余战斗时（Boss 奖励）：下一幕的地图尚未生成，前瞻按下一幕的遭遇池、可能的 Boss 和刚打完这一幕的
     地图结构继续进行，并以 `next_act_needs_from_pools` 披露（2026-10-13 按实际行为更正；此前写的是“退化为只评当前牌组”）。
2. **协同只做说明，不另加分**：引擎按整副牌组计算，现有牌之间的协同已体现在适合度里；另加协同维度
   会重复计分。理由中改为列出“牌组里哪些牌让这张牌更强”（逐张移除比较得到），供用户理解。
3. 切换门禁不变：v2 命中不低于 v1 且没有明显错误排第一。

#### 补充：战斗长度随牌组输出变化（2026-10-12，用户决定）

背景：需求里的战斗回合数是固定参数（普通 4、精英 5、Boss 7），所以“打得更快、少挨几回合”这层好处
没有进入分数，输出牌与跳过的分差被压得很小。38 个局面里，现有牌组的每回合输出都低于输出需求
（预计战斗长度是标准的 1.2～3 倍）。

决定：

- 预计战斗长度（相对标准回合数）＝ 输出需求 ÷（前期输出＋成长）每回合伤害，限制在参数
  `fight_tempo` 的 `[min, max]`（初始 0.5～2.0）之内。输出需求本身就是“敌方总血量 ÷ 标准回合数”，
  所以这个比值就是“打完需要几个标准战斗长度”。
- 只影响防御维度中**没挡住的部分**：防御满足度 ＝ 1 −（1 − 格挡 ÷ 防御需求）× 预计战斗长度。
  格挡已达到需求时不受影响；其余维度不变。
- 这仍是按每回合期望值的解析计算，不模拟战斗、不预测敌人行动，Out of Scope 不变。
- 理由中，格挡不变而战斗长度改变时，改为说明“预计战斗长度为标准的 a → b 倍”。
- 同时试过把防御需求从敌方攻击的 60% 提高到 80%／100%：标准答案集上名次只是互相换位，没有净改善，
  不采用，`block_share` 维持 0.6。

#### 补充：对局历史数据与“拿牌门槛”（2026-10-13，用户决定）

背景：游戏在存档目录的 `saves/history/*.run` 为每一局保存完整记录（每次选牌的候选与取舍、牌组变化、
每场战斗的遭遇、回合数与受到的伤害）。`scripts/import_run_history.py` 只读地把单人对局重放成选牌局面
和战斗结果，输出到 `build/history/`（玩家个人记录，不入库）。重放出的牌组必须与文件结尾的牌组一致，
否则整局舍弃。用户决定先用获胜的对局：13 局、225 个选牌局面、271 场可比对的战斗。

发现：

- 玩家在获胜对局中跳过了 45% 的选牌，第一／二／三幕依次为 25%／51%／73%；候选含稀有牌时只有 19%。
- v2 算出的“最好一张比跳过高几分”与玩家的取舍方向一致（高出 4 分以上时跳过率 9%，1 分以内 56%），
  但 v2 只要高出 0 分就推荐拿；v1 的分数与跳过基本无关，且从不推荐跳过。
- 战斗回合数：引擎预测与实际的相关系数第一幕 0.75、整体 0.62；越到后期越高估（Boss 高估约三成），
  来自尚未完整计入的牌。实际平均为普通 3.9、精英 5.5、Boss 8.8 回合。
- 实际受到的伤害约为敌方总攻击的两成，与引擎算出的格挡高低看不出关系；与牌组击杀速度关系明显
  （预测最慢的一组平均受伤 19，最快的 7～8）。

决定：

- **拿牌门槛**：候选的分数要比跳过高出门槛才推荐拿，门槛为参数 `pick_margin_by_act`
  （初始第一／二／三幕 1／2／3 分，之后各幕沿用最后一档）。门槛加在“跳过”的分数上并作为一条依据列出。
  数值由人工设定：取整、随幕递增，没有逐题拟合。检验方式是把 13 局分成两半互相验证，并在两批没有
  参与设定的数据上检查（当前版本真机 79 题、历史中输掉的对局 284 题），三处都明显提高。
- 把防御改为“总有约两成伤害漏过”并把 Boss／精英回合数改为实测值的做法试过：与玩家选择的一致程度
  没有提高（三批数据都略降），不采用，`block_share`、`fight_turns` 维持原值；上述发现留作后续依据。
- “不从对局自动学习权重”不变：历史数据只用于检验和人工设定参数，程序不会自行更新参数。

#### 补充：取消旧版回退，选牌不再使用社群评价（2026-10-22，用户决定）

- 发布的选牌建议只由牌组适合度（`card_reward:deck_fitness_1`）给出。此前“旧版保留为回退”的做法取消：
  新内核无法评分时显示“无法判断”（`uncertain`），出错时同样显示“无法判断”并在数据缺口中注明 `deck_fitness_error`，
  不再由依赖社群评价的旧版代为作答。本节取代上文“旧版保留为回退”与用户故事 39 中关于回退的部分。
- 曾评估“决定拿牌后按 社群评价 + 2 × 适合度 挑选”的组合做法（历史全部局 204 → 215 题、真机 34 → 36 题）。
  用户决定不采用：评分中不使用社群评价。
- 旧版选牌策略只保留在标准答案集评估中作为比较基线，不进入宿主的策略注册表。
- 此改动随下一次构建发布（策略包版本与发行指纹届时更新）；已安装的 0.3.12 仍含回退。

#### 补充：路线战斗风险下限与商店金币价值（2026-10-13，用户决定，TASK-026）

背景：真机一局中，金币 300～1000 时路线建议仍避开商店，且第二幕起各候选全部显示 100 分。原因是
牌组能力对战斗风险的扣减没有上限（战斗越多路线越“安全”），而商店的金币加成最多只有 3。

决定：

- 战斗节点（普通、精英、Boss）的风险在扣除牌组能力后不低于 0：牌组再强也只能让战斗没有风险，
  不能让战斗本身变成加分。被截掉的部分作为因子列出。
- 商店的金币加成为 `min(max, 1 + 金币 ÷ gold_per_point)`（初始每 100 金币 1 点、上限 8），
  仍不假定库存。同一条路线上金币只在第一间商店计入一次。
- 路线风险参数与选牌参数一样，由 `data/guide_mechanics.json` 直接进入发行数据库。
- 不改变三种路线模式、图校验和协议；路线的能力估计接入统一估值仍留待后续。

#### 补充：篝火休息与锻造的生命门槛（2026-10-22，用户决定直接推进）

背景：对局历史中 42 局、260 次篝火选择（休息 113、锻造 147）。按休息前生命比例，休息率依次为：
低于 40% 全部休息，40–50% 为 79%，50–60% 为 70%，60–70% 为 39%，70–80% 为 18%，80% 以上 1%
（`scripts/analyze_rest_choices.py`）。此前初查：牌组引擎算出的最佳升级价值与取舍无关。

决定：

- 篝火同时提供休息与锻造时，只按生命比例排序：生命低于 `heal_below_hp_ratio`（60%）推荐休息，
  否则推荐锻造，理由写明“生命 X%，低于／不低于 60%”。被推荐的一项领先另一项 `rule_margin`（5 分）；
  只有其中一项、或离开与特殊动作的评分不变。锻造只在至少一个升级有正收益时由规则推荐，否则按效果比较。
- 参数为 Guide 自有参数 `campfire_rest_rule_v1`，人工设定；缺失或非法时休息与锻造都不评分并披露缺口，
  生命未知时披露 `campfire_rule:hp_missing`。规则不读取地图，地图缺失不产生缺口。
- 检验：按对局 ID 分两半（新旧各半、交替各半），阈值从一半的表格读出（四个半份都读出 60%），
  在另一半上与玩家一致 80.6–87.3%；“低于 50% 就休息”为 76.1–82.5%，总是锻造 54–59%，总是休息 41–46%。
- 试过但不采用：下一行就是 Boss 时休息更多（生命 50–70% 时 70% 对 39%），但为 Boss 前单设门槛
  在另一半上两升两降，没有稳定提高；前方精英、幕、药水数、最大生命看不出稳定影响。
- 锻造的价值改为“能估值的最佳升级”作为下限：牌组中有升级效果未建模的牌时不再整体判为无法判断，
  而是披露 `deck_edit:upgrade_delta_partial:<张数>`（只有在没有任何牌能估值时才是 `upgrade_delta_unknown`）。
  此前 260 次中 255 次因此“无法判断”；改后用实际篝火策略重放，257 次给出建议，与玩家一致 216 次（84%）。
- 能力仍为 `pending_validation`（不在游戏画面显示），需真机验证后才开启。

## 3. 用户体验

### 3.1 启动

P0 内部验收阶段仍允许用户分别启动游戏和无主窗口的 `STS2 Guide.exe`。首个公开
Beta 的目标体验升级为：

1. 安装程序自动定位或让用户选择 STS2 目录，并安装可核验的 Mod 与 Guide；
2. 用户可以先启动 STS2，也可以先启动 `STS2 Guide.exe`；
3. Guide 以单实例托盘程序驻留；检测到游戏后启动实时 Worker，游戏关闭后停止 Worker，
   但托盘继续低占用待机；
4. 再次运行 EXE 只唤起已有实例，不生成第二个 Host；
5. 只有用户从托盘选择“完全退出”时，控制器和全部 Worker 才一起结束；
6. 托盘提供连接、游戏版本、Mod/协议/数据版本、更新和脱敏诊断状态，但不替代局内建议。

最终用户不应手动启动 Python、FastAPI、Vite 或终端脚本。Vue 前端不属于 P0
运行依赖。

### 3.2 选牌界面

- 推荐面板由 Mod 创建为 Godot `Control`，锚定游戏原生选牌界面；
- 面板采用贴住视口左边缘的半透明抽屉，宽度根据内容与视口自适应，并设置合理的最小值、最大值和视口占比；
- 抽屉默认展开，点击右缘箭头后向左滑出并仅保留贴边按钮，再次点击滑入；
- 按游戏原始顺序显示实际数量的候选牌名称和“跳过”；
- 默认每项只显示 `0–100` 的“推荐分”，不显示长解释、置信度或社区分拆；按需展开依据见第 2.3 节；
- 四个分数互相独立，不要求总和为 100，也不表示胜率；
- 分数只保证同一次真实决策内的候选可比较，不承诺跨局、跨角色或跨版本的相同数值
  具有相同含义；
- 最高分项突出显示；
- 数据不足时显示 `--`，不得伪造精确值；
- P0 标准场景是普通战斗/奖励后的三张牌加跳过；Neow 祝福等开局特殊决策不属于
  P0 推荐范围，若出现同类选牌 UI，必须安全隐藏或显示 `--`，不得显示上一屏或错误候选；
- 选择完成或界面关闭后自动隐藏；
- 除抽屉开关和按需评分依据展开外，面板只显示信息，不覆盖原按钮，不接受替用户做选择的交互。

P0 先以真机效果为准确定间距、字号、颜色和高亮方式，视觉参数不写死为产品约束。
在面板不遮挡原生操作区域的前提下，字号应优先保证窗口模式下的可读性。

### 3.3 长期产品方向：实时策略副驾驶

P0 的选牌闭环是第一个可交付纵向切片，不是产品的最终边界。STS2 Guide 的长期形态是
一个本地、只读、主动感知关键决策的实时策略副驾驶，而不是攻略问答机器人、自动代打
工具或若干互不相干的评分面板。

产品围绕一局游戏形成连续闭环：

```text
感知真实游戏状态
  → 维护当前局世界状态
  → 识别当前决策场景
  → 调用对应的本地策略工具
  → 比较实际可选候选
  → 在统一游戏内抽屉主动展示建议
  → 观察决策关闭并继续维护状态
```

P1 及以后覆盖路线、Neow、商店、篝火、Boss 遗物和事件，但仍由用户自己操作。
默认界面保持安静，只显示即时排序和推荐度；解释属于按需展开的第二层，不得阻塞实时
建议。RAG/LLM 只可为解释提供攻略证据，不能成为决策 Agent 成立的前提。

### 3.4 统一决策体验

当前左侧选牌抽屉长期升级为统一的 `Context Drawer`：

- 没有受支持决策时隐藏或保持最小化；
- 只显示当前真实场景的候选，不跨场景复用上一条建议；
- 根据选牌、地图、商店、篝火等场景切换内容，而不是新增多个浮窗；
- 用户界面名称使用“策略侧栏”；`Context Drawer` 只作为内部工程名称；
- 默认保持候选列表、推荐度和必要状态提示；最关键的 2–3 条加减分原因按需展开；
- 用户主动展开后才显示关键因子、替代方案和可选攻略解释；
- 状态、候选或身份校验不足时显示 `--` 或隐藏，绝不猜测。

路线模式在策略侧栏内切换，首版使用三个目标型软偏好：

- 智能均衡：按当前局面自动平衡生存和成长；
- 稳健生存：降低路线风险，倾向休整并减少高风险节点；
- 激进成长：在安全底线内提高精英和高收益节点权重。

模式不是硬命令，不能在明显无法承受时强迫推荐危险路线。同一局保存继续后保留当前
模式，胜利、失败、放弃或新开一局后恢复“智能均衡”。玩家没有按建议选择时，Guide
必须把实际进入节点作为新事实，废弃旧路线并保留当前模式重新规划。

地图只绘制一条从当前真实节点通往本幕 Boss 的“当前规划”，突出下一节点；不同时绘制
备选完整路线。路线在节点、牌库、HP、遗物、药水或其他重要状态变化后重新计算。覆盖层
优先使用独立只读 Godot 绘制层；只有经程序集和真机验证后才可复用游戏坐标/渲染 API，
不得模拟原生绘制按钮、修改用户涂画或拦截地图点击。

## 4. P0 系统架构

```text
┌──────────────────────── STS2 进程 ────────────────────────┐
│                                                           │
│  游戏状态 ──> 只读 C# Mod ──> 临时事件文件                │
│      │                                │                   │
│      └── 原生选牌界面 <── Godot 推荐面板 <── 建议文件      │
│                                                           │
└───────────────────────────────────────────────────────────┘
                                   ▲
                                   │ 本地文件协议
                                   ▼
┌──────────────────── STS2 Guide 后台 EXE ──────────────────┐
│ 协议校验 → 当前局检查点 → 本地推荐器 → 原子写回建议       │
│                    │                                      │
│                    ├── 本地社区先验                        │
│                    ├── 结构化卡牌/遗物数据                 │
│                    └── 当前局状态规则                      │
└───────────────────────────────────────────────────────────┘
                     │
                     ├── 当前局：单一可替换检查点
                     └── 结束后：仅 SQLite 最终结果摘要
```

### 4.1 只读 Mod

负责：

- 读取角色、难度、楼层、生命、金币、能量；
- 读取完整牌组、升级、附魔和负面状态；
- 读取遗物及其动态状态、药水、Run Modifiers；
- 读取选牌候选、候选顺序、是否允许跳过、奖励来源；
- 监听选择、跳过、界面关闭和一局结束；
- 捕获当前节点、地图节点、真实边、可选下一节点和 Boss；
- 将事件原子写入本地目录；
- 读取建议并绘制游戏内面板。

不负责：

- 计算分数；
- 调用网络、LLM 或数据库；
- 修改游戏状态、选项、存档或用户输入；
- 自动点击或代替用户操作。

### 4.2 后台 EXE

负责：

- 启动并托管文件桥接、协议校验、检查点和推荐器；
- 对事件做顺序、重复和过期检查；
- 从本地数据源加载结构化先验；
- 在本机完成评分并原子写回建议；
- 游戏中断后恢复同一局；
- 在胜利、失败或放弃时清理中间状态并保存最终摘要；
- 统一记录本地日志和可诊断错误。

P0 可以由 Python 打包为单一后台 EXE，不要求为了“桌面原生”重写全部推荐逻辑。

公开 Beta 的托盘控制器和实时 Worker 可以位于同一个 EXE/进程，也可以是受控子组件；
无论实现形式如何，都必须由用户级单实例机制统一拥有生命周期。游戏关闭时 Worker
停止，托盘继续待机；完全退出必须等待并回收所有后台任务，不允许留下旧 Host。

### 4.4 版本、更新与兼容性

发行包必须携带唯一兼容清单，至少记录：

- Guide 版本；
- 支持的精确游戏版本和当前程序集哈希；
- Mod 版本；
- Mod/Host 协议版本；
- SQLite 静态数据快照版本；
- 推荐策略版本。

Mod、Host、数据库或协议任一项不匹配时必须清除旧 advice、停止推荐并指出具体不兼容项。
未知游戏版本不得“尽力继续”。托盘可以提供可关闭的更新检查，但更新模块只读取版本
清单，不上传任何局内数据；实时 Mod 和推荐 Worker 始终不依赖网络。

首版正式支持原版内容。检测到第三方玩法或内容 Mod 时标记为未验证环境；未知实体显示
`--`，不得按名称猜测。无法可靠确认环境时失败关闭。

### 4.3 Vue、FastAPI、RAG 和 LLM

- Vue 保留为以后攻略问答或历史查看的候选界面，不进入 P0 实时链路；
- FastAPI 可作为开发调试接口保留，但最终 P0 启动不依赖独立 API 进程；
- RAG 只处理攻略语义检索和可选解释，不决定实时分数；
- LLM 以后只能用于用户主动展开的解释，不得阻塞或改变实时基础推荐。

## 5. 数据边界

不同数据按用途存放，不能因为“都能存”就统一塞进向量库或关系库。

| 数据 | 存储 | 生命周期 | 原因 |
|---|---|---|---|
| 卡牌、遗物、药水、角色、敌人、遭遇、事件、章节、机制和来源元数据 | SQLite | 长期 | 稳定 ID、过滤、关联、规则计算和版本查询 |
| 社区结构化统计 | SQLite（源快照可为 JSON） | 长期 | 数值查询，不需要语义检索 |
| 本地人工整理的 tier 数据 | Git 忽略的 JSON | 用户本机 | 可选私有输入，不随项目分发 |
| 攻略正文和语义切片 | 原文快照 + 向量索引 | 长期、可重建 | 用于 RAG 语义检索 |
| 当前局完整状态 | 单一原子 JSON 检查点 | 当前局 | 需要恢复，不需要历史查询 |
| 待处理事件 | 临时事件队列 | 处理后删除 | 避免快速事件覆盖，不作为历史 |
| 每次选牌分数和选择过程 | 默认不持久化 | 当前决策 | P0 不收集训练样本 |
| 最终对局摘要 | SQLite | 长期 | 战绩查询和以后统计 |

### 5.1 当前局检查点

每一局只维护一个可替换检查点，而不是不断向 SQLite 追加状态历史。

协议必须明确区分“权威完整快照”和“事件通知”：

- 完整快照是当前局事实，事件只负责通知状态或决策发生变化；
- 开局、继续游戏、中途接入和关键决策出现时，必须能取得同一 revision 的完整关键状态；
- 每个决策绑定 `run_id + state_revision + decision_id + 候选稳定 ID`；
- 不得把新牌库与旧地图静默拼成一个看似完整的 `WorldState`；
- 关键数据（角色、牌库、候选、Run/决策身份）缺失时停止推荐并显示“正在同步”；
- 非关键上下文缺失时可以降级，但必须列出 data gap，并让对应因素不参与加减分；
- Host 可在游戏前、游戏后或一局中途启动；没有足够快照时等待同步，不复用上一局建议。

检查点至少包含：

- 可跨游戏重启识别的稳定游戏 Run ID；
- 最近处理的事件序号；
- 当前角色、难度、章节、楼层、生命、金币和能量；
- 当前牌组、遗物、药水、Modifiers；
- 当前节点和已读取的地图快照；
- 当前未关闭决策及其候选；
- 游戏版本，仅用于兼容性诊断。

写入必须使用“临时文件 + 原子替换”。游戏或后台程序异常退出后，只要该局仍可继续，
下次启动就恢复检查点；不能继续或已结束时清理检查点。

当前 Mod 每次启动随机生成的 ID 不能满足恢复要求。P0 必须从游戏可稳定读取的数据
构造或取得 Run ID，并验证不会把两局游戏合并。

### 5.2 最终结果

胜利、失败或放弃后：

1. 写入一条最终结果摘要；
2. 确认写入成功；
3. 删除检查点、临时事件和未完成建议；
4. 不保留逐楼层状态、逐次选牌历史或完整事件流。

最终摘要字段：

- 结果：`win` / `loss` / `abandon`；
- 角色；
- Ascension；
- 最终楼层；
- 最终分数；
- 开始和结束时间；
- 最终牌组；
- 最终遗物；
- 最终药水；
- 游戏版本（内部保留，默认不展示）。

P0 不进行个人习惯学习，也不积累 `decision_outcomes` 训练样本。以后若加入个性化，
优先保存风险偏好、精英路线偏好、牌组精简程度等聚合特征，而不是完整原始对局。

## 6. 本地数据源策略

### 6.1 可随项目使用的数据

- Spire Codex 的结构化实体和社区统计作为默认可重建来源；
- 本项目自己的透明规则、卡牌标签和协同表；
- 经允许发布或项目自行创作的攻略文本。

Spire Codex 只作为开发期/构建期数据源，最终实时后台不得依赖联网查询。导入流程应：

- 优先使用按语言提供的批量 JSON 导出，并记录来源 URL、抓取时间、内容哈希和数据版本；
- 把卡牌、遗物、药水、角色、敌人行动、遭遇池、事件选项树、章节和机制常量作为
  结构化事实导入 SQLite；
- 保留原始 JSON 为可重建快照，但不把第三方图片资源或完整游戏资源打入产品；
- 对 API 缺失、字段变化和不完整记录安全降级，不能在运行时临时请求网络补数据；
- 遵守 Spire Codex API 条款和 Mega Crit 游戏数据权属说明，并在发布物中保留数据来源说明。

每个发行版携带与兼容清单绑定的 SQLite 快照。玩家运行时只从该本地数据库查询；游戏
版本变化后的结构化实体、效果标签和风险常量只能通过新版 Guide 更新，不能在玩家电脑上
临时抓取。社区数据始终是可移除的弱先验，缺失时推荐链路必须正常工作。

公开发行快照不是 Spire Codex 或游戏资料的离线镜像。构建时可以从完整开发快照生成效果
标签和关系表，但安装包只保留当前已启用推荐能力实际需要的稳定 ID、名称、数值字段、
派生效果标签、遭遇关系、路线风险常量和聚合统计；必须删除攻略/事件正文、对话、完整
描述、语义文本、图片地址以及未启用能力的实体类别。开发数据库与发行数据库必须分开，
发行构建应以自动测试证明叙事文本和源 JSON 没有进入安装包。每次新增 capability 时重新
审查所需最小字段，不能为了未来可能使用而提前打包完整资料库。

Spire Codex 的社区攻略与游戏实体数据不能混为同一种授权来源。攻略正文只有在逐篇确认
作者、来源和可再分发边界后，才进入原文快照和向量索引；事件剧情文本的权威副本仍随
事件结构保存在 SQLite/源快照中，不因为文本较长就自动进入向量库。

### 6.2 本机 Mobalytics tier 文件

P0 允许像参考项目一样读取本地 tier 文件，但采用以下边界：

- 数据由开发者在本机人工整理，不编写自动爬虫；
- 建议路径：`data/local/mobalytics_card_tiers.json`；
- 路径加入 `.gitignore`，文件不提交、不打包、不随公开版本分发；
- 只保存推荐所需的卡牌稳定 ID、角色、tier、记录时间和来源地址，不复制网页正文；
- 文件缺失、过期或格式错误时，推荐器必须自动退化到 Spire Codex + 自有规则；
- 使用稳定卡牌 ID 关联，不以中文名、英文名模糊匹配；
- tier 只转为有限权重的基础先验，不能直接决定最终选择；
- 具体 tier 到分数的映射由本项目自行定义和测试，不复制 BoberInSpire 的常量。

建议的最小文件结构：

```json
{
  "schema_version": 1,
  "source": "mobalytics-manual-local",
  "source_url": "https://mobalytics.gg/slay-the-spire-2/tier-lists/cards",
  "captured_at": "2026-07-03T00:00:00+08:00",
  "entries": [
    {
      "card_id": "stable-card-id",
      "character_id": "stable-character-id",
      "tier": "A"
    }
  ]
}
```

这是一项“当前开发电脑优先”的 P0 取舍，不等于将第三方内容纳入项目许可证。
公开发布时默认不依赖该文件。

### 6.3 参考 BoberInSpire 的边界

[BoberInSpire](https://github.com/S0ul3r/BoberInSpire)只用于验证产品链路和理解
“Mod 导出状态 → Python 本地计算 → 覆盖层展示”的可行性。

可以借鉴：

- 本地状态导出和消费的产品思路；
- tier 只作为基础值，再结合当前牌组调整；
- 实时推荐不依赖 LLM。
- 公开源码中暴露出的“可能存在的游戏类型、事件和字段名称”只能作为 API 调研线索。

不得复制：

- 对方代码；
- 对方生成或硬编码的流派表；
- 对方具体权重、tier 分数锚点和数据文件；
- 对方 UI 资源或品牌表达。
- 对方通过名称搜索、动态反射或兜底猜测得到的字段，不能直接作为本项目的生产 API。

本项目的差异化是：游戏内 Godot 面板、稳定 ID、多流派信号并存、正式的跳过候选、
当前局检查点和结束后仅保留摘要。

## 7. 选牌推荐策略

### 7.1 输出定义

每次选牌输出四个同尺度候选：

1. 左侧卡牌；
2. 中间卡牌；
3. 右侧卡牌；
4. 跳过。

推荐分表示“这个选项对当前局面的适合程度”，不是胜率，也不是社区排名。

### 7.2 透明评分原则

P0 使用可追踪的有界加法模型，不把尚未校准的规则包装成概率：

```text
卡牌适配分
  = 50
  + 卡牌基础效果
  + 当前牌组功能缺口
  + 卡牌与牌组协同
  + 当前角色与遗物协同
  + HP、章节和近期路线压力
  + 有界社区先验
```

社区先验只负责在局面信号接近时提供弱排序，不使用固定百分比伪装精度，也不能单独
触发跳过。所有因子必须返回代码、增减值和解释，调权必须通过固定场景集和真机样例
验证，不能因少量个人对局自动学习。

内部必须保存每个候选的完整分数贡献和原因代码；策略侧栏只展示最终推荐分和最重要的
2–3 条原因。推荐分是当前局面下的相对辅助刻度，不是胜率。

当前局适配至少考虑：

- 卡牌的输出、格挡、抽牌、能量、成长、范围、费用变化和资源代价；
- 当前攻防缺口；
- 能量曲线与出牌负担；
- 抽牌、能量和资源循环；
- 候选与已有卡牌、遗物的协同；
- 章节、Boss 和已知路线对短期能力的需求；
- 升级、附魔和负面状态；
- 重复牌收益或冗余；
- 牌组膨胀代价。

社区高 tier 不能单独强制抓取，社区低 tier 也不能在强协同时被硬性禁止。

卡牌和遗物的效果标签属于结构化事实，写入 SQLite 并由稳定 ID 查询。标签优先从
结构化字段生成，描述规则只作为可版本化、可测试的补充；RAG 和 LLM 不参与实时
标签生成或评分。

路线压力必须按当前可选路径分别统计，再聚合为可达比例和平均风险；不能把互斥分支
上的精英、Boss 和小怪全部视为必经节点。同一威胁对同一候选只能产生一组路线因子，
不得同时叠加“通用危险”和“精英/Boss 危险”。

战前敌人信息必须区分“已知事实”和“遭遇估计”。当前 Act 的 Boss 可以按游戏提供的
稳定身份参与威胁建模；普通怪物和精英在进入战斗前不能被当成已知具体敌人。它们只能
依据当前 Act 的真实遭遇池、已确认的游戏规则和本局已击败精英集合计算候选威胁：
未耗尽的精英池应排除本局已击败精英，池耗尽后才允许出现重复可能。此模型必须输出
候选集合或聚合威胁，不能伪造下一战的确定敌人。

P0/P1 的敌人机制只用于改善选牌和路线的战前风险判断，不提供战斗内逐回合出牌建议。
静态敌人行为与机制可以进入 SQLite；P0 不保存敌人逐回合行动历史。

P0 读取并保留药水状态，但药水是一次性资源，其“提供某种效果”不等于“支持继续
抓取同类卡牌”。在建立经过场景验证的资源替代模型前，药水不参与选牌评分。

自身耗竭、虚无和“与虚无牌交互”必须是不同标签。只有明确区分效果提供者与收益方
后才允许计算协同；无法由当前局状态验证的条件标签只保存事实，不进入实时加分。

### 7.3 多流派并存

P0 不把牌组过早分类为唯一流派。推荐器同时维护多个协同信号：

- 每个信号由已有牌、遗物和资源状态提供证据；
- 证据越强，该信号对候选的影响越大；
- 多个信号可以同时生效；
- 没有足够证据时回到通用攻防、曲线和资源规则。

五个角色共享同一个评分内核，不复制五套规则。每个角色允许注册一个薄机制适配层，
只负责把充能球、星数、厄运及其他角色专属资源转换为通用、可解释的能力和协同信号。
公开声明“全角色支持”前，每个角色都必须通过：

1. 牌库、遗物、药水、HP、地图和跳过的参数化通用规则测试；
2. 角色核心资源与主要机制的专项固定场景；
3. 至少一次完整第一幕的真机状态、选牌和路线烟测。

### 7.4 跳过

跳过是正式第四候选，分数不得固定。它与卡牌使用同一 `0–100` 适配尺度，至少考虑：

- 保持牌组精简的收益；
- 当前牌组大小和重复度；
- 三张候选对牌组造成的冗余或负面影响；
- 当前牌组是否急需补强；
- 当前章节和即将面对的威胁；
- 候选中是否存在明确协同或关键功能牌。

社区先验不能单独把卡牌压到跳过之下。面板高亮必须服从推荐器给出的最终候选，
不得仅对包括不可用“跳过”在内的显示分数取最大值。

## 8. 协议与实时性

当前目标生产协议是 JSON Schema v9。v4 在既有状态、决策和地图结构上增加
`boss_encounter_ids`，用于表达游戏已知的当前 Act Boss 遭遇；v5 进一步分离不可变
`event_id`、稳定 `decision_id` 和候选实例 `candidate_id`。这些字段不能用于把普通怪物或
精英伪装成确定遭遇。v6 增加 `route_choice` 与真实 `origin_node_id`；v7 增加权威快照、
 成功提交 revision、生产者/游戏程序集身份和跨组件 release fingerprint；v8 增加显式
`guide_preferences.route_mode`，把用户选择的路线软偏好纳入同局权威状态；v9 将所有实时
决策迁移到严格通用候选 envelope，并增加类型化成本、效果与父子决策身份。Python 对
v1-v8 的兼容只用于离线录制回放；生产 Host 只接受兼容清单指定的精确 v9。

### 8.1 事件

P0 实际处理：

- `card_reward`；
- `decision_closed`；
- `run_ended`。

P0 同时正确捕获 `map_snapshot` 所需数据，但不输出路线推荐。商店、篝火、Boss 遗物
等决策事件进入 P1 后再成为推荐工具，不能仅因协议中预留名称就宣称已经支持。

临时事件队列用于避免快速事件互相覆盖。后台确认处理后应删除事件；队列不是审计库。

### 8.2 建议响应

建议协议至少包含：

- 协议版本；
- 对应 Run ID；
- 对应事件 ID；
- 候选稳定 ID 和原始顺序；
- 候选牌与跳过的推荐分；
- 最高分候选；
- 生成时间；
- 推荐器版本；
- 数据不足或降级标记。

Mod 必须拒绝显示属于旧事件、旧 Run 或候选不匹配的建议，避免“上一组牌的分数”
显示在下一组选项旁。

实时生产 schema v9 在 v7 完整状态基础上必须显式携带：

- `snapshot_kind = "complete"`，表示该事件中的状态是同一观察时刻的权威快照，不是增量；
- 单调递增的 `state_revision`，当前实现可以等于成功提交的 event sequence，但不能使用
  写盘失败的尝试次数；
- `producer_id`、`producer_version` 和游戏程序集 SHA-256；
- 规范化 `release_fingerprint`，覆盖 Guide、Game、Mod、protocol、SQLite 快照和 policy；
- Host 根据唯一发行兼容清单计算的兼容结果；Mod 只报告身份事实，不能自行宣称兼容。
- `guide_preferences.route_mode`，只允许 `balanced`、`survival`、`growth`；同局保存继续
  恢复，胜利、失败、放弃或新 Run 重置为 `balanced`。
- 通用 `candidates` envelope、类型化 `cost` / `effects` 和可选 `decision_parent`；生产
  处理链不得继续依赖 Card Reward 专用顶层 `options`。

Schema 与运行时模型必须使用相同严格类型。Schema 拒绝的字符串数字、`0/1` 布尔、
NaN/Infinity 或缺失关键快照字段，Pydantic/消费者也必须拒绝。v1-v8 只用于离线录制回放；
实时 Host 只接受兼容清单指定的精确生产版本。事件、当前局 checkpoint、advice 和 Mod
显示端必须核对同一个 release fingerprint；升级后不得把旧策略结果重新标记为当前兼容。

### 8.3 性能目标

- 实时推荐不访问网络；
- 本地事件被发现到建议文件写回的 P95 不超过 300 ms；
- 单次纯评分应明显低于总预算，并通过基准测试记录；
- 数据源加载在后台启动时完成，不能每次选牌重新解析全部文件；
- 推荐器异常时游戏继续正常运行，面板显示 `--` 或隐藏。

## 9. 路线能力边界

P0 只做正确采集，不做路线推荐。

必须采集：

- 当前节点；
- 完整节点列表；
- 节点类型和坐标；
- 游戏提供的真实连边；
- 当前可到达的下一节点；
- 当前 Act 的 Boss。

进入具体战斗前，地图节点只能说明普通战、精英或 Boss 类型。除已知 Boss 外，不得把
普通怪物或精英预测成某个确定敌人；后续威胁模型只能基于遭遇池和已击败精英排除规则
计算期望风险。

禁止：

- 读取失败时伪造“下一行全部相连”；
- 用猜测边运行推荐器；
- 在前端展示看似可用的三种路线策略；
- 将地图界面打开等同于地图数据已正确读取。

路线推荐在 P1 使用经过回放和真机验证的图数据实现，并与生命、牌组、遗物和章节需求联动。
建议结果只把当前最高推荐的完整路线叠加在真实地图节点和连边上，并随地图布局和视口变化
重新定位；其他候选只保留为内部排序事实，不绘制第二条路线。该叠加层属于 STS2 Guide 的
只读 Godot Overlay，不写入游戏原生“绘制/擦除/清除”数据，不覆盖玩家涂画，也不修改
存档；显示和隐藏由统一 `Context Drawer` 控制。

## 10. P0 改造计划

### P0-1：消除架构冲突

目标：让代码的数据生命周期和运行方式先与本规格一致。

涉及文件：

- `realtime/processor.py`
- `realtime/session.py`
- `realtime/file_bridge.py`
- `storage/relational.py`
- `api.py`
- `frontend/src/App.vue`
- `docs/realtime-architecture.md`
- `docs/data-architecture.md`

改造：

- 停止把运行状态、每次决策和选择结果追加到 SQLite；
- 引入单一当前局检查点；
- SQLite 只保留静态结构化数据和最终结果；
- 将 Vue/FastAPI 从 P0 用户运行链路中隔离；
- 暂停未验证的路线推荐和对应 UI；
- 删除未被运行时引用且会猜测地图连边的旧路线推荐器；
- 保留旧功能时必须标记为开发/实验入口。

验证：

- 连续多个选牌事件不会产生历史 SQLite 行；
- 当前局始终只有一个检查点；
- 后台服务重启后可恢复该检查点；
- P0 实时路径无网络请求；
- 旧路线推荐不会出现在用户界面。

### P0-2：稳定状态协议和生命周期

涉及文件：

- `protocol/state-event.schema.json`

## 11. P1 计划

P1 在 P0 稳定后扩展“决策类型”，不先扩展模型复杂度。默认交付仍采用一个决策类型一个
完整纵向闭环。2026-07-31 用户明确决定在下一轮集中真机前批量完成后续自动层，因此允许
路线、Neow、商店、篝火与事件在同一个扩展任务中连续实现，但必须共用一次协议迁移、
一个生命周期、一个策略注册表和一个 Context Drawer；不得铺开多套半成品管线或复制
`card_reward` 处理分支。

批量实现只改变开发调度，不改变完成定义。每种决策仍必须分别记录真实 API 证据、自动
测试、安装态和真机结果；未通过真机的切片必须由 capability/compatibility gate 保持关闭，
不能因其他切片通过而被连带标记完成。

### 11.1 P0.5：扩展前的决策内核收口

P0 真机验收后、P1 增加新决策前，先进行一次不扩大用户功能范围的架构收口：

1. 建立统一 `WorldState`，集中表达角色、牌组、遗物、资源、地图和当前场景；
2. 将状态观察与决策生命周期分开，区分状态快照、决策打开、更新、关闭和 Run 生命周期；
3. 建立通用 `DecisionRequest`，由稳定决策 ID、决策类型、候选、约束和状态引用组成；
4. 建立策略注册机制，让 Card、Route、Shop、Campfire 等策略实现共同接口；
5. 建立通用 `Recommendation`，统一候选身份、排序、适配分、多维评价、数据缺口和版本；
6. 将现有 Card Reward 迁移为第一个策略插件，迁移前后推荐结果和 P0 体验保持兼容；
7. 将左侧面板抽象为统一 `Context Drawer`，P0 仍只渲染 Card Reward；
8. 隔离 Vue、FastAPI 和 RAG 实验入口，避免它们成为实时内核依赖。

P0.5 不重写已验证的真实游戏 API，不改变只读边界，不同时加入新的评分功能。若重构
需要协议升级，必须提供旧 P0 夹具兼容测试和真机回归，不能仅凭代码结构宣告完成。

P0.5 的通用契约还必须满足以下硬约束，未满足前不得开始 P1 策略实现：

1. `event_id` 表示一次不可变观察，`decision_id` 表示一次可跨多次观察更新的稳定决策；
2. 决策打开、更新和关闭必须同时校验 `run_id + decision_id + sequence`，跨 Run 关闭失败
   关闭；同一结果的重复关闭幂等，冲突结果不得覆盖首次结果；
3. 当前检查点只保存一个通用 `current_decision` 及最近关闭防重信息，不得硬编码
   `card_reward`，也不得写入决策历史；
4. 所有实时决策通过统一的 event adapter 构建 `WorldState` 和 `DecisionRequest`，共享策略
   调用、生命周期和 advice envelope，不能为商店、路线或篝火复制完整处理分支；
5. `Recommendation` 的候选必须全部来自请求；跳过、离开等动作只有在真实可用时才作为
   显式候选，通用注册表不得凭决策类型虚构候选；
6. advice envelope 对决策类型保持通用，Card Reward 旧 `advice` 只能作为可选兼容层；
   schema、示例、生产者、消费者和真实实例校验必须同步；
7. `Context Drawer` 的显示、更新和关闭必须绑定决策 handle；旧场景回调不得覆盖或销毁
   新场景抽屉，advice 缺失、错配或失效时必须立即显示 `--` 或隐藏；
8. 自动发布门禁必须执行真实 schema 校验，并让打包 EXE 走过单实例锁和完整初始化路径，
   不能只检查源码字符串或 `--help`。

### 11.2.1 批量扩展的通用候选协议

后续决策不得继续把顶层 `options` 固定为卡牌结构。下一次生产协议只做一次通用候选迁移，
每个候选至少包含：

- `candidate_id`：同一决策内稳定且唯一；
- `kind`：card、relic、potion、service、route_node、rest_action、neow_blessing、
  event_option 等受控枚举；
- `entity_id` 与 `label`：实体稳定 ID 和用户可读名称；没有实体时允许只使用受控动作 ID；
- `eligible` 与结构化不可用原因；
- `cost`：金币、HP、最大 HP、资源或其他明确成本的类型化表示；
- `payload`：按候选 kind 严格校验的最小结构化事实，不能接受任意自由 JSON。

Card Reward 必须迁移到同一候选 envelope，旧 v1-v8 仅用于离线回放。Merchant、Rest Site、
Neow 和 Event 不得在 `realtime.processor` 中各自复制身份、checkpoint、发布或清理代码；
event adapter 只负责把真实 Mod 事实转换为 `WorldState + DecisionRequest`。

跨决策共享一个 `ResourceBudget` 视图，至少表达当前金币、HP/最大 HP、药水槽、牌组大小、
可升级牌、移除收益和路线风险。它是当前状态的确定性派生，不单独持久化历史，也不能把
未来随机奖励当成已知事实。

### 11.2.2 新决策的产品语义

- **Neow**：祝福选择是 `neow_blessing`；祝福随后真正打开的选牌、遗物或其他奖励仍由其
  对应决策类型处理，并以 parent context 标明来源，不能复用上一局或上一屏候选。
- **商店**：卡牌、遗物、药水和移除服务是异构候选；只有游戏真实允许购买的项目可被
  推荐。离开只在原生界面确实允许时作为候选。推荐必须考虑保留金币和同店互斥购买后的
  动态重算，不把“最高 tier”直接等同于购买。
- **篝火**：第一阶段推荐真实可用动作；选择 Smith 等二阶段动作后，再对游戏真实候选
  产生独立子决策。Rest 的治疗量、升级价值和特殊遗物动作只使用当前版本真实 API。
- **事件**：以真实 event/page/option 稳定 ID 为核心。能由静态结构化数据确认的成本收益
  才进入确定性评分；描述不完整、随机结果或版本不匹配时必须降低置信度并报告 data gap，
  不允许 LLM 猜测隐藏结果。

所有候选变化都必须产生同一 decision 的 UPDATED；购买、选择、离开或场景关闭产生
CLOSED。多阶段场景使用显式 parent decision/context，不用 UI 文本或屏幕位置推断。

### 11.3 P1.0：路线完整闭环

P1.0 只实现路线，不同时实现 Neow、商店或篝火。用户体验为：

1. 只有游戏处于“必须从真实下一节点中选择”的状态时才生成路线建议；手动预览地图只
   更新地图观察，不创建伪决策；
2. 策略侧栏显示当前路线模式、真实可选下一节点及推荐度；
3. 独立只读 `RouteMapOverlay` 在真实地图节点之间只显示一条当前主路线；
4. 用户仍由游戏原界面自己点击，Guide 不自动选择、不修改原生绘制内容；
5. 状态、边、候选或视觉锚点不完整时显示 `--` 或隐藏线条，不根据截图坐标补画。

开始 Mod 生产实现前必须从当前本机程序集和真机探针确认：

- 区分“可实际选择下一节点”和“仅打开地图预览”的公开状态；
- 玩家选择真实 `MapPoint` 后的安全 Postfix 触发点；
- 保存继续、切换场景和无选择关闭的时序；
- 地图模型节点与实际 Godot `NMapPoint` 视觉节点的稳定映射；
- 地图滚动，以及视口、分辨率和窗口变化导致的 Godot 全局变换与坐标转换；
- 同一次 origin 选择机会的稳定 identity 来源，以及同 Act 是否可能重访 origin。

找不到这些 API 时任务必须停止并报告，不得用字段名列表、UI 文本、截图位置或宽泛反射
猜测。`NMapScreen.Open` 继续只作为地图观察点，不能单独证明路线决策已经打开。

STS2 `0.108.0` 曾由本机程序集确认不存在用户可操作的地图级 Zoom API；该证据不自动
适用于当前 `0.110.1`。新版本必须重新检查地图拖动、窗口、viewport/content scaling 和
可能新增的 Zoom 行为。Overlay 仍必须对所有真实 transform 变化逐帧重新锚定，不能主动
设置游戏节点 `Scale` 来伪造兼容。

路线决策最初在 schema v6 引入；目标生产发送统一使用 v9，并继续满足：

- 保留既有 `map_choice` 作为地图观察兼容事件；
- 新增 `route_choice`，仅表示真实可操作路线决策；
- `route_choice` 必须包含稳定 `decision_id`、完整 `map_context` 和非空的
  `available_next_node_ids`；
- 路线候选由 event adapter 从真实下一节点 ID 构建，`candidate_id = node_id`，不虚构
  “跳过”或“离开”；
- 选择关闭事件使用同一 `decision_id`，`selected_candidate_id` 为真实节点 ID，并引用最新
  观察 `parent_event_id`；
- 同一当前位置的重复观察产生 `UPDATED`，选择完成后产生 `CLOSED`，新当前位置产生新决策；
- 地图上下文与决策生命周期必须作为两个独立状态变换，在同一次原子 checkpoint 写入中
  一并提交；不能使用互斥 `if/elif` 丢失其中一个，也不能拆成两次写盘暴露中间状态。

`event_id` 每次观察都变化；`decision_id` 必须表示“从同一 origin 选择下一节点”的同一次
机会。当前版本尚未证明同一 Act 内 origin 绝不重访，因此路线使用 Mod 生成的 GUID，并以
Run、Act、真实 origin、规范化候选集合和地图指纹从唯一当前检查点严格恢复；不得使用
RunState/Godot 运行时对象 ID，也不得直接拼接 `{run_id}:route:{act}:{origin}`。Act 初始
可操作地图已有真实 `CurrentMapPoint`（真机样本为 `0:3`），必须使用真实节点；若可操作
界面稳定后 origin 仍为空，则不创建路线决策，不能用 sentinel 伪造。
保存回主菜单以 `closed_unknown` 结束当前观察会话（不表示选点或整局结束），继续时按真实
恢复界面建立新决策；仅后台异常重启且游戏决策未关闭时恢复原 decision ID。

Recommendation contract v2 在通用候选评价之外增加可选类型化展示数据。当前代码仍
携带历史 `backup_path_node_ids` 兼容字段；PB-2 必须将公开路线展示收口为单条主路线，
旧字段只允许为空或在协议迁移期读取，不得继续绘制第二条路线：

```json
{
  "presentation": {
    "kind": "route_paths",
    "origin_node_id": "0:0",
    "primary_path_node_ids": ["0:1", "1:2", "2:2"],
    "backup_path_node_ids": [],
    "paths": [
      {"candidate_id": "0:1", "node_ids": ["0:1", "1:2", "2:2"], "score": 68.0},
      {"candidate_id": "0:3", "node_ids": ["0:3", "1:4", "2:4"], "score": 61.0}
    ]
  }
}
```

主路线必须从推荐的真实下一节点开始；路径中每一条边都必须存在于当前快照，并最终到达
真实 Boss 节点。Card Reward 在迁移期接受 contract v1/v2，Route 消费者只接受 v2 路线
展示结构。`paths` 仍可按候选 ID 携带内部完整路径行，用于排序和拓扑校验，但地图只渲染
推荐候选的主路径；不确定输出必须让 `recommended_candidate_id` 为 `null`，且路径数组
为空。

路线策略先采用确定、透明、可回放的有界图搜索。输入包括 HP/最大 HP、牌组即时输出、
防御、AOE、成长与资源能力、遗物、药水、金币、节点类型、已知 Boss 和一个版本化默认
风险 profile。PB-2 增加“智能均衡 / 稳健生存 / 激进成长”三种软偏好；路线仍须保留
生存底线，不能把模式实现为节点数量硬约束。
普通怪物与精英只使用房间类型和真实遭遇池的期望风险，不得伪造确定敌人。关键图数据
缺失、Boss 不可达或图不满足已验证约束时，返回空推荐和明确 `data_gaps`。

路线所需的敌人机制、遭遇池和可配置风险常量属于静态结构化事实，进入 SQLite；当前局
地图、当前位置、候选和路径只存在于 `active-run.json`/当前 advice 中，结束后不保存逐次
路线历史。攻略长文和向量索引不进入 P1.0 实时依赖。

`RouteMapOverlay` 只接收节点 ID 和真实边，不接收 Python 计算的屏幕坐标；它绑定当前
`decision_id` 与真实地图 screen owner，`MouseFilter=Ignore`，随地图滚动以及 viewport、
分辨率和窗口变化造成的全局 transform 变化重新定位。
旧界面回调、错配 advice、非法路径或 Drawer 关闭必须清除 Overlay，且不得修改玩家使用
游戏原生绘制/擦除/清除工具产生的内容。

P1.0/PB-2 自动验收至少覆盖 schema v1-v8 回放兼容、v9 生产握手、预览地图不创建决策、
稳定 ID 更新与关闭、跨 Run/过期 parent/非法候选拒绝、真实边与 Boss 可达性、只绘制当前
主路线、确定场景复现、owner-scoped advice 清理、无网络和 P95 不超过 300 ms。真机至少覆盖 Act
初始路线、完成节点后的下一次路线、仅预览地图、选择后清理、地图滚动与窗口/视口变化、
原生绘制不受影响、Route → 战斗 → Card Reward 不残留旧路线，以及保存继续。

协议迁移期可以保留“备选候选排序不同”的内部测试，但 PB-2 的用户界面不得绘制备选线。
路线模式必须在同局保存继续后恢复，新局重置；玩家偏离推荐后以实际节点重算完整剩余路径。

为减少反复启动游戏，PB-2 与 PB-3 可以在自动层连续实施，但不得因此跳过门禁：两者代码
完成后统一进行 `0.110.1` 隔离探针、正式安装和五角色组合真机回归；在组合真机完成前，
TASK-007、PB-2、PB-3 均不能标记为交付完成。

P1.0 明确不做自动选路线、战斗逐回合出牌、普通怪/精英确定身份预测、胜率、RAG/LLM、
自学习、多人模式或未验证 API 的反射 fallback。

### 11.4 推荐模型的演进方向

推荐器内部逐步从“所有信号直接累加成单分”演进为可审计的多维评价：

- 即时战力；
- 生存能力；
- 长期成长；
- 资源效率；
- 牌组负担；
- 机制协同；
- 路线适配；
- 数据完整度与不确定性。

界面仍可显示一个简洁推荐度，但该数值只是当前策略和风险偏好下的排序刻度，不是胜率。
任何新维度都必须有真实输入、上下界、回放场景和负例，不能用更多权重掩盖数据缺失。

### 11.5 开发回放模式

正式产品默认继续遵守“不保存逐决策历史”的数据边界。为支持算法回归和真机问题定位，
允许后续增加显式开启、与正式运行隔离的开发回放模式：

- 默认关闭，不进入公开发行的正常数据流；
- 只在开发者主动开启时记录状态、候选、因子、建议和已确认选择；
- 数据仅保存在本机，可一键清理，不自动上传、不自动训练；
- 回放数据不能混入 `run_summaries`，也不能改变实时推荐；
- 对外发布前必须验证关闭状态不会产生这些记录。

## 12. P2 计划

1. 攻略 RAG：
   - 扩充真正的攻略语料，而不是只有实体解释；
   - 保留原文、来源、语言、版本和章节边界；
   - 长文按标题和语义段落切分，不能只按固定字符截断；
   - 用于用户主动询问“为什么”，不进入实时硬依赖。
2. 可选 LLM 解释：
   - 引用检索证据；
   - 无证据时明确拒绝编造；
   - 网络失败不影响基础推荐。
3. 只读 Strategy Agent：
   - Agent 只在用户主动展开“为什么/替代方案”时运行，不参与 P95 ≤ 300 ms 的实时排序；
   - 输入是冻结的 `WorldState + Recommendation + decision_id`，不能自行重新读取屏幕或猜测
     已变化状态；
   - 工具只允许精确查询 SQLite 实体/机制、读取当前 Recommendation 因子和检索有来源的
     攻略切片；不得调用游戏选择 API、写存档、写当前局状态或访问任意文件；
   - 输出采用 `ExplainResponse`，必须带所解释的候选 ID、关键因子、替代方案、data gaps、
     来源与生成时间；返回前再次校验当前 decision，过期结果不得显示；
   - 没有 LLM、网络超时或攻略库缺失时，退化为确定性因子解释与结构化来源，不影响推荐；
   - Hybrid Search、Reranker、HyDE 或多步规划只有在固定解释评测证明单一检索不足时才能
     启用，不能默认串联所有组件。
4. 个性化：
   - 用户明确开启后只保存聚合偏好；
   - 不默认保存完整决策历史；
   - 与全局推荐规则分层，可随时重置。
5. 在具有足够、合规且按版本隔离的数据后，再评估候选排序模型和胜率模型；
6. 多人模式和跨平台支持最后评估，不属于当前承诺。

## 13. 当前明确不做

- 不自动抓取或分发 Mobalytics、slaythespire-2.com 的内容；
- 不复制 BoberInSpire 代码、权重、流派表或数据；
- 不把大模型放入实时选牌主链路；
- 不把推荐分宣传为胜率；
- 不让 Mod 自动做选择或修改游戏；
- 不在 P0 保存逐事件、逐楼层、逐次选择历史；
- 不在样本不足时做“自我学习”；
- 不为了简历中的 Agent 标签堆叠 Hybrid Search、Reranker、HyDE 等组件；
- 不在地图读取不可信时继续堆路线功能；
- 不把“协议预留”“界面已写”或“代码存在”等同于功能已真机完成。

## 14. 后续决策原则

1. 先保证状态真实，再讨论推荐算法；
2. 默认先完成一个闭环再增加决策类型；批量开发必须共用内核并让每个切片独立门禁；
3. 先保证无网络的确定性基线，再增加 RAG/LLM 解释；
4. 结构化数据走稳定 ID 和关系查询，长文本才走向量检索；
5. 当前局状态短期保存，最终摘要长期保存；
6. 所有外部数据必须有来源、版本、更新时间和可降级策略；
7. 所有推荐都必须能在数据不足或组件故障时安全退出；
8. 游戏 API 必须先通过程序集、真实对象日志或真机回归验证；找不到 API 时安全降级，
   不用字段名、界面文本、截图位置或反射猜测伪造状态；
9. 产品价值来自及时、可靠的局面建议，而不是组件数量。
