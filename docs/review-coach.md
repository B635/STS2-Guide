# 赛后复盘教练：设计说明与面试问答

> 说明：设计取舍和评估方法由作者决定并验收，代码实现有 AI 协助（Claude Code）。
> 决策记录见 [`tasks/TASK-028-review-coach/README.md`](tasks/TASK-028-review-coach/README.md)，
> 所有数字都能从 `coach/eval/` 里存下的输出重算。

## 1. 它是什么

打完一局《杀戮尖塔 2》后，读游戏自己写的对局记录（`.run`），做两件事：

- `coach review <file.run>`：生成一份 HTML 复盘报告，列出最多 5 个“值得想一想”的决定，
  每条说明引擎为什么更看好另一个选项、改了什么引擎就会同意你、下次可以注意什么。
- `coach ask <file.run>`：在终端里追问这一局（“我这局防御是从哪里开始不够的？”），多轮对话。

实时产品（游戏内建议）刻意不用 LLM：要在 300 ms 内给结果，而且结果必须固定、可复现。
教练是赛后离线工具，解释和追问才是 LLM 适合的位置。两者共用同一个确定性评分引擎。

## 2. 架构

```
.run 文件
   │
   ▼
Python 评分引擎（advisor/，确定性，无 LLM）
   │  包成 10 个 MCP 工具（review/mcp_server.py，stdio 子进程）
   ▼
TypeScript 教练（coach/）
   ├─ 预处理（程序）：重算整局 → 给每个决定分层 → 取严格标记，最多 5 条
   ├─ 调查 Agent ×N（并行）：每条标记一个循环，检验“如果当时…”，交出结构化结论
   ├─ 验证器（程序）：结论里的因子、数字、卡名必须对得上工具结果；不通过退回修一次，再不通过丢弃
   ├─ 总结（一次模型调用，同样核对；失败则用程序生成的句子）
   └─ HTML 报告（程序套模板，模型不写 HTML）＋ JSONL 执行记录

coach ask：
   主 Agent（先列计划 → 查资料 / 派调查 Agent → 写草稿）
     → 程序核对数字和名称 → 审查 Agent 找没有根据的句子 → 最多重写一次 → 仍不成立的句子删掉并注明
   记忆：最近 4 轮问答；跨局玩家笔记（程序根据已验证结论写入，最多 20 条）
```

| 模块 | 文件 |
|---|---|
| 引擎重算与分层 | `review/run_review.py` |
| 查询与敏感度测试工具 | `review/tools.py`、`review/mcp_server.py` |
| MCP 客户端 | `coach/src/engine.ts` |
| 调查 Agent 循环 | `coach/src/agent.ts` |
| 结论格式 / 验证器 | `coach/src/finding.ts`、`coach/src/verifier.ts` |
| 主 Agent / 审查 Agent / 笔记 | `coach/src/ask.ts`、`critic.ts`、`notes.ts` |
| 评估 | `coach/src/evaluate.ts`、`askeval.ts` |

## 3. 关键设计取舍

**哪些交给程序，哪些交给模型。** 找出哪些决定值得讲、报告的标题句（“引擎认为 X 比你选的 Y 高 N 分”）、
引擎没算全的提示、HTML，全部由程序产生。模型只做需要判断的事：挑哪种假设去检验、把原因讲成人话。

**严格标记。** 引擎和这位玩家的选择只有约一半一致，所以不能把每次不同都说成问题。只有同时满足
“两个选项都完整计分、引擎信心不是低、分差 ≥ 2 分或超过该幕门槛”才列出，措辞是“引擎认为”，不写“失误”。
分差只比牌组本身的分数，不含人为设定的“跳过门槛”（含门槛时 34 条“建议跳过”的标记里只有 8 条站得住）。
历史 43 局量测：每局中位数 2 条，21% 的局一条都没有，那种局就如实写“没有引擎有把握的分歧”，不跑模型。

**敏感度测试（“如果当时…”）。** 模型可以改动当时的牌组再让引擎重算同一个决定，但只能用这局真实出现过的东西
（牌组里的牌、之前出现过的选项、升级）。不做“照引擎选会怎样”的整局重播：之后的战斗、血量、路线都会变，结论站不住。

**固定资料由程序预取。** 第一版让模型自己调用所有工具。量了 55 条标记的执行记录后发现：
选项比较、当时牌组、可用改动三个工具每条都被调用，顺序几乎一样，而 `what_if` 几乎都只试一次。
于是把这三样改成程序先查好，模型的 6 次额度只用于检验假设。结果：每条检验的改动 1.0 → 3.5 种，
开始能找到“改了什么引擎就同意你”，开发集费用 $0.064 → $0.046。

**验证器是程序，不是另一个模型。** 结果固定、可复现，通过率直接就是“有没有编造”的指标。规则：
理由对应的因子必须是两个选项差距最大的前 3 项；引用的工具结果里必须有这个因子；
文字里的每个数字、每个卡牌／遗物／药水名称必须出现在引用的结果里；禁用词。

**对话为什么要三个角色。** 调查部分本来就有（复盘用的同一个循环），可以并行。
对话的回答是自由文字，程序只能核对数字和名称，“理由说不说得通”需要另一个模型来审，
所以加审查 Agent；顺序是程序核对在前、模型审查在后。

**记忆不让模型自由写。** 跨局笔记只由程序根据通过验证的结论生成，避免把没核对过的话存下来再反复引用。

**自己写循环，不用 LangGraph。** 流程只有固定几步，循环一两百行；步数上限、强制提交、退回修正都要精确控制。
用 `openai` SDK（DeepSeek 兼容）＋官方 MCP SDK ＋ zod。

## 4. 评估

对局在动手调 prompt 之前就固定切分（种子 28，没看标记）：开发集 10 局、测试集 15 局（含全部 3 局当前版本）。
prompt 只在开发集上调。每局的完整输出（证据、执行记录）都存下来，指标从存下的输出计算，不用 API 密钥也能重算。

**复盘（`deepseek-flash`，测试集 31 条标记）**

| | 通过验证 | 一次通过 | 15 局费用 | 每局秒数 |
|---|---|---|---|---|
| 最终版（p4） | 29/31（93.5%） | 12 | $0.084 | 8.4 |
| 改接法前（p3） | 30/31 | 14 | $0.093 | 7.6 |
| `deepseek-v4-pro`（p3） | 28/31 | 12 | $0.375 | 12.9 |

- 进入报告的结论 100% 通过验证（没通过的被丢弃并在报告注明）。
- 验证器在测试集上实际拦下的编造：flash 3 个数字；pro 4 个数字、6 个卡名。
- 贵 4 倍的 pro 没有更好，主线用 flash。
- 测试集跑了两次：第二次是因为架构变更（预取），不是根据测试结果调 prompt；两次的指标都保留。
- 一次通过率测试集（约 40%）低于开发集（63–79%），如实记录。

**对话（开发集 20 个固定问题）**

| 指标 | 结果 |
|---|---|
| 最终回答通过程序核对 | 100% |
| 草稿被审查 Agent 退回 | 35%（同一 prompt 多次运行在 20%–45% 之间） |
| 退回的 7 题里，重写后仍有句子被删 | 2 题 |
| 引擎答不了的问题如实说答不了 | 4/4 |
| 每题费用 / 时间 | $0.006 / 约 11 秒 |

**人工评分**：作者本人对测试集每条结论评“有用／没用／引擎错了”（1 位评分者，不宣称评分者间一致性）。
结果待补。

## 5. 已知限制

- 引擎本身和玩家只有约一半一致；教练解释的是引擎的看法，引擎错了它也会跟着错（人工评分的“引擎错了”就是量这个）。
- 休息点：升级价值只算得到下限，260 次里 251 次信心为低，所以只进附录。商店只比较“买或离开”。
- 旧版本的对局用当前版本的数据评分；资料库没有的卡牌或 Boss 会跳过并在报告注明。
- 程序核对抓不到用汉字写的数字（“两局”）和模型自己数出来的次数。
- 审查 Agent 的退回率不稳定，20 题只能看方向。
- 找到翻转点的比例不高（测试集 31 条里 3 条），其余如实写“试了几种改动，首选没变”。

## 6. 面试问答

**为什么实时建议不用 LLM？**
延迟预算 300 ms，同一局面必须给同一结果，而且错了要能查出是哪条规则。这些 LLM 都做不到。LLM 用在赛后：不赶时间，任务是解释和回答开放问题。

**这算 Agent 还是流程？**
两种都有，而且是量出来的分工。复盘部分大半是固定流程，只有“检验哪种假设”交给模型；对话部分问题是开放的，由主 Agent 自己计划、选工具、决定派几个调查 Agent。原则是路径固定的地方用程序，路径会分岔的地方才用 Agent。

**怎么防止模型编造？**
三层。结构上：标题句和分数由程序写，模型不碰。验证上：每个理由要指明依据哪次工具结果，程序核对因子、数字、名称。流程上：不通过就把错误清单退回修一次，再不通过就丢弃并在报告注明。测试集上验证器确实拦下过编造的数字和卡名。

**为什么用 MCP，而不是直接调用 Python？**
引擎是 Python，Agent 是 TypeScript，MCP 是现成的跨语言工具协议：工具的参数和说明写在 schema 里，TS 端直接转成模型的工具定义。走 stdio 子进程，不开端口。同一组工具也能直接接到其他支持 MCP 的客户端。

**Agent 的循环怎么停？工具出错怎么办？**
每个循环都有具名的上限：调查 Agent 6 次工具调用、1 次修正；主 Agent 每题 8 轮、8 次工具调用、4 个调查 Agent、1 次重写。额度用完后强制调用提交工具。工具报错原样回给模型（例如“这张牌在第 15 层之前没出现过，可选的有…”），模型据此改参数。

**为什么最终结果用工具调用提交，而不是让模型输出 JSON？**
提交工具的参数就是 zod schema，格式错误和验证错误都能当作工具结果退回，模型在同一个对话里修正。实际踩过的坑：嵌套对象被模型写成字符串，改成平铺字段后解决。

**怎么评估的？怎么保证不是对着答案调？**
对局先切分再动手，prompt 只在开发集上调，测试集只在定稿后跑。指标四类：有没有编造（验证通过率）、该讲的有没有讲到、作者人工评分、换模型比较。输出全部存档，指标可重算。测试集因为架构变更跑过第二次，文档里写明了原因并保留了两次的数字。

**多 Agent 是不是为了多而多？**
调查 Agent 是复用的，并行能省时间；审查 Agent 是因为自由文字的“理由是否成立”程序判断不了。没有做“规划 Agent”“写作 Agent”这种拆分，因为一次调用就能做好的事不需要拆。

**如果重做，会改什么？**
一开始就先量执行记录再决定哪些工具交给模型；评估集再大一些（现在每局平均只有 2 条标记，20–30 条的样本只能看方向）；审查 Agent 需要用人工评分校准。

**DeepSeek 有什么坑？**
`deepseek-flash` 默认开思考模式，思考模式下不支持强制 `tool_choice`，`temperature` 也不生效。主线关闭思考模式，强制提交才可用。

## 7. 运行

```bash
# 准备：Python 3.10+（MCP 服务器）与 Node 20+
uv venv .venv-coach --python 3.12 && uv pip install --python .venv-coach/Scripts/python.exe -r review/requirements.txt
cd coach && npm ci

# 环境变量 DEEPSEEK_API_KEY（或仓库根目录的 .env）
npx tsx src/cli.ts review eval/runs/dev/1773034032.run          # 报告在 coach/out/reports/
npx tsx src/cli.ts review eval/runs/dev/1773034032.run --no-llm # 只跑确定性预处理，不需要密钥
npx tsx src/cli.ts ask eval/runs/dev/1773034032.run             # 终端对话
npx tsx src/cli.ts eval metrics dev                             # 从存下的输出重算指标
```

Docker（CI 上构建并做冒烟测试）：`docker build -f coach/Dockerfile -t sts2-coach .`
